# 夜航 Nebula · 设计语言

> 安卓端「口袋酒馆」的独立设计体系。**不沿用桌面端风格**（需求文档 §设计体系）。
> 本册是 T15.1 的交付物之一，也是后续所有移动端 UI 的唯一 token 来源。
>
> 实现纪律：**UI 代码里不许出现裸色值/裸字号**，一律引用本册的 CSS 变量。
> 违反这条的后果不是"不好看"，是下次调主题要全库搜色值，必然漏。

---

## 0. 设计意图（一句话）

**深夜里唯一亮着的那块光。**

用户场景：躺在床上、通勤地铁、关灯的房间里，单手拿手机跟一个角色说话。
所以整套语言围绕三件事：**低亮度下不刺眼**、**单手够得着**、**不打断沉浸**。

由此定了三条不可让步的取向：

| 取向 | 具体表现 | 反例（明确不做） |
|---|---|---|
| 暗夜优先 | 默认深色，且**不做亮色主题切换**（v1） | 白天模式白底、跟随系统浅色 |
| 光来自内容 | 强调色只出现在"值得看一眼"的地方（新消息、正在生成、当前 Tab） | 满屏渐变按钮、彩虹描边 |
| 结构靠层次不靠线 | 用明度差与玻璃层叠分开区域，**少用 1px 边框** | 到处是分隔线、卡片全描边 |

## 1. 色彩

### 1.1 背景层次（从最深到最上）

```css
--nb-void:      #07060B;  /* 最底：App 背景，接近黑但不是纯黑（纯黑在 OLED 上滚动会有拖影感） */
--nb-abyss:     #0C0A14;  /* 页面级背景 */
--nb-surface-1: #14121E;  /* 卡片底层 */
--nb-surface-2: #1C1929;  /* 卡片上层 / 输入框 */
--nb-surface-3: #262235;  /* 悬停 / 按下 / 选中项 */
```

> 选 `#07060B` 而不是 `#000000` 的原因：纯黑背景上的深色玻璃层会**完全消失**，
> 失去"雾面玻璃"的存在感；留一点蓝紫底，玻璃才有东西可以折射。

### 1.2 强调：星云紫 → 青

```css
--nb-nebula-a:  #8B5CF6;  /* 星云紫（渐变起点） */
--nb-nebula-b:  #22D3EE;  /* 极光青（渐变终点） */
--nb-nebula-mid:#A78BFA;  /* 中间过渡（用于单色场景） */

--nb-grad-primary: linear-gradient(135deg, var(--nb-nebula-a) 0%, var(--nb-nebula-b) 100%);
--nb-grad-soft:    linear-gradient(135deg, rgba(139,92,246,.22) 0%, rgba(34,211,238,.16) 100%);
--nb-grad-glow:    radial-gradient(60% 60% at 50% 0%, rgba(139,92,246,.35) 0%, transparent 100%);
```

**用在哪（穷举，不许扩大）**：

1. 当前 Tab 的图标与指示条；
2. 「正在生成」的光标/呼吸点；
3. 主行动按钮的**文字**（按钮底仍是玻璃，不铺满渐变）；
4. 语音按住说话时的波形；
5. 空状态的插画光晕。

**不用在**：普通按钮底色、卡片边框、列表分隔、滚动条。

### 1.3 语义色

```css
--nb-ok:    #34D399;  /* 保存成功、连接正常 */
--nb-warn:  #FBBF24;  /* 未配置语音、ST 正在启动 */
--nb-danger:#F87171;  /* 删除、连接失败 */
--nb-info:  #60A5FA;  /* 提示 */
```

语义色只用于**图标与短文本**，不做大面积填充（暗色下大面积高饱和会晃眼）。

### 1.4 文本层级

```css
--nb-text-1: #F4F2FB;  /* 主文本、消息正文 */
--nb-text-2: #A8A2C0;  /* 次要：时间、副标题 */
--nb-text-3: #6E6885;  /* 弱：占位符、禁用 */
--nb-text-on-accent: #0A0810;  /* 铺在渐变上的文字（深色，保证对比） */
```

对比度要求：`--nb-text-1` 对 `--nb-abyss` ≥ 12:1；`--nb-text-2` ≥ 5:1；
`--nb-text-3` **仅用于非关键信息**（不作正文字色）。

## 2. 玻璃质感（本设计语言的签名）

```css
--nb-glass-bg:     rgba(255, 255, 255, 0.045);
--nb-glass-bg-2:   rgba(255, 255, 255, 0.07);
--nb-glass-border: rgba(255, 255, 255, 0.085);
--nb-glass-blur:   24px;
--nb-glass-sat:    140%;
```

标准玻璃卡片：

```css
.nb-glass {
  background: var(--nb-glass-bg);
  backdrop-filter: blur(var(--nb-glass-blur)) saturate(var(--nb-glass-sat));
  -webkit-backdrop-filter: blur(var(--nb-glass-blur)) saturate(var(--nb-glass-sat));
  border: 1px solid var(--nb-glass-border);
  border-radius: var(--nb-radius-lg);
}
```

**两条实践约束**（不写进代码就会踩）：

1. **`backdrop-filter` 在 Android WebView 上性能不稳**：屏幕上同时存在的玻璃层
   **不超过 3 个**。列表项（几十个）不用玻璃，用 `--nb-surface-1` 纯色。
2. 玻璃层**必须压在有色背景上**才有意义。压在纯 `--nb-void` 上等于只有边框，
   这时改用 `--nb-surface-1`（省一次合成开销）。

## 3. 尺度

### 3.1 字号阶梯

```css
--nb-fs-11: 11px;   /* 角标、Tab 文字 */
--nb-fs-12: 12px;   /* 时间戳、辅助说明 */
--nb-fs-14: 14px;   /* 次要正文、列表副标题 */
--nb-fs-16: 16px;   /* 正文默认（输入框、消息） */
--nb-fs-20: 20px;   /* 区块标题 */
--nb-fs-24: 24px;   /* 页面大标题 */
--nb-fs-32: 32px;   /* 空状态主文案 */
```

行高：正文 `1.6`（中文长文本需要更松），标题 `1.25`，单行控件 `1.2`。

> 为什么正文是 16 而不是 14：这是**手机**，且用户常在暗光下看。
> 桌面端的 14px 搬到手机上普遍偏小，会让人不自觉把手机拿近。

### 3.2 间距（4 的倍数）

```css
--nb-sp-1: 4px;   --nb-sp-2: 8px;   --nb-sp-3: 12px;
--nb-sp-4: 16px;  --nb-sp-5: 20px;  --nb-sp-6: 24px;
--nb-sp-8: 32px;  --nb-sp-10: 40px;
```

页面左右内边距固定 `--nb-sp-4`（16px）；卡片内边距 `--nb-sp-4`；
列表项垂直 `--nb-sp-3`。

### 3.3 圆角

```css
--nb-radius-sm: 8px;    /* 小标签、输入框内元素 */
--nb-radius-md: 12px;   /* 输入框 */
--nb-radius-lg: 16px;   /* 卡片 */
--nb-radius-xl: 20px;   /* 大卡片、消息气泡 */
--nb-radius-pill: 999px;/* 按钮、Tab 指示条 */
```

### 3.4 触屏目标（硬约束）

| 元素 | 最小尺寸 |
|---|---|
| 任何可点区域 | **44 × 44 px** |
| 底部 Tab | 高 56px + 安全区 |
| 发送 / 麦克风按钮 | 48 × 48 px |
| 消息气泡的「重新生成」等次级操作 | 44 × 44（视觉可以小，热区必须够） |

> 44px 是 iOS HIG 与 Android 无障碍指南的公共下限。视觉上可以只画 24px 图标，
> 但 `.hit-area` 必须撑到 44。列表项之间不加分隔线时，靠 44 的热区防止误触。

### 3.5 跨设备（**硬约束**，用户三次明令）

> 我这里提一嘴，你做的动画应该要兼容别的手机系统或者设备，
> 不能就只用我连到电脑上的这个设备为基准
>
> 所有 UI 设计不能只依据我当前连到电脑上的这台手机，要保证不同手机可以兼容
>
> 再次重申，所有的 UI 设计不能只依据我当前连到电脑上的这台手机，要保证不同手机可以兼容

**判据不是"在我这台机器上看着对"，而是"在下面的区间里都不坏"。**

需要覆盖的区间：

| 维度 | 区间 | 为什么会变 |
|---|---|---|
| 屏幕宽度 | 320 / 360 / 393 / 412 / 480 / 768 / 1024 dp | 老机型、分屏、折叠屏、平板 |
| 字号 | 12 ~ 32px（含 1.3×/1.5×/2× 系统字体缩放） | Android 设置里可调 |
| 视口高度 | 全高 / 键盘弹起后约一半 / 320px | 软键盘、横屏 |
| 刷新率 | 20 / 30 / 60 / 90 / 120 fps | 见 §4 动效纪律 |

**三条具体做法**：

```text
① 尺寸优先用 token / 百分比 / flex，不写裸像素
   例外：1px 边框、图标字形、以及"内容本身就这么大"的徽标

② 必须写像素时，**锚在可读性上，不锚在某一台设备上**
   ✗ const MIN_WIDTH = 160;                    ← 360dp/16px 凑出来的数
   ✓ minWidth = 9 * fontSize + chrome          ← 系统字体放大时跟着变大

③ 算出来的值要由"视口"封顶
   width = min(max(anchorWidth, minWidth), viewportWidth - edge * 2)
   顺序不能反：先 max 再 min，否则小屏上会顶出屏幕右边
```

**已落实的判据**：

- `test/popover-responsive.test.mjs`：7 种屏宽 × 8 档字号 × 5 种触发器宽度
  全组合，验证"文字放得下 / 不溢出 / 字号变大则下限变大"
- `test/page-easing-robust.test.mjs`：五档刷新率下每帧位移的最差 cv
- `test/nebula-walkthrough.test.mjs` 走查 2：可点热区不许写死小于 44 的像素

**一条反例（记下来免得再犯）**：修「人设下拉竖排」时，第一版写的是
`POPOVER_MIN_WIDTH = 160`。它在 320dp 小屏、1.3× 字体缩放、14px 字号档上
全都不成立 —— 而用户当场就提醒了这件事。**"凑一个能过的数"永远不是修好。**

## 4. 动效

```css
--nb-dur-micro: 120ms;   /* 按下反馈、图标切换 */
--nb-dur-base:  200ms;   /* 展开/收起、抽屉 */
--nb-dur-page:  320ms;   /* 页面转场 */
--nb-ease-out:  cubic-bezier(0.16, 1, 0.3, 1);      /* 进场（快速起步、缓慢收尾） */
--nb-ease-in:   cubic-bezier(0.7, 0, 0.84, 0);      /* 退场 */
--nb-ease-spring: cubic-bezier(0.34, 1.56, 0.64, 1);/* 轻微回弹，只用于语音按钮与 Tab */
```

**动效纪律**：

- 只做**位移 + 透明度 + 缩放**，不做宽度/高度动画（会触发 layout，中端机上能看出卡顿）；
- 「正在生成」用呼吸点而不是骨架屏（骨架屏在大段文字流里会跳）；
- 尊重系统「减少动态效果」：`@media (prefers-reduced-motion: reduce)` 下把
  `--nb-dur-*` 全设为 `1ms`，**只保留透明度变化**。

```text
│ 状态栏（透明，内容可延伸）    │
├─────────────────────────┤
│ 页面标题区（大标题 24）      │  ← 可随滚动收起为 16 的顶栏
│                         │
│                         │
│      内容区（可滚动）        │
│                         │
│                         │
├─────────────────────────┤
│ 聊天 · 卡片 · 仓库 · 我的   │  ← 56px + 安全区，玻璃底
└─────────────────────────┘
```

| Tab | 图标语义 | 主职责 |
|---|---|---|
| 聊天 | 对话气泡 | 角色选择 → 会话列表 → 聊天 |
| 卡片 | 卡片叠层 | 我的卡：新建/编辑/导出/推送 |
| 仓库 | 云/箱 | 服务端同步：账户、令牌、拉取/上传 |
| 我的 | 人像 | 语音配置、ST 引擎状态、主题、关于 |

Tab 激活态：图标换 `--nb-grad-primary` + 文字变 `--nb-text-1` + 顶部 3px 指示条（圆角 pill）。
**不做**缩放弹跳（次级动效只给语音按钮）。

### 5.1 安全区

```css
padding-bottom: calc(56px + env(safe-area-inset-bottom));
```

列表底部额外留 `--nb-sp-10`，避免最后一项被 Tab 挡住（这是移动端最常见的"内容点不到"）。

## 6. 手势

| 手势 | 作用 | 优先级说明 |
|---|---|---|
| 左缘右滑 | 返回上一页 | **最高**。任何列表的左滑操作都必须让位（见下） |
| 上拉底部抽屉 | 审计面板（编辑器内） | 中 |
| 长按消息 | 复制 / 编辑 / 删除 | 中 |
| 按住说话 | 语音输入 | 高（在输入区内，与左缘手势不冲突） |
| 双击消息 | 编辑该条 | 低（可发现性差，仅作快捷方式） |

**冲突处置（2026-10-28 用户确认，决策 #271）**：swipe 切候选（聊天面板）与左缘返回冲突。
定法是**只有从屏幕最左 20px 起手才算返回**；消息气泡自身的左滑从气泡内部起手，
两者不重叠。

```text
左缘 0–20px 起手右滑  →  返回（最高优先级，任何页面都让位）
消息气泡内左滑         →  切 swipe 候选
气泡内右滑             →  不占用（留给系统返回手势的备选）
```

**验收要求**：T15.5 必须实测两条轨迹 —— 「从气泡左缘起手左滑」与「从屏幕左缘起手右滑」，
确认前者切候选、后者返回，且不被浏览器/系统手势抢走。
移动端最容易被抢的就是这一类边缘手势，只在模拟器里拖鼠标是测不出来的。
要录屏作为证据（需求文档要求录屏验收）。

### 6.3 桌面端 → 触屏的形态映射（T15.2 的适配依据）

需求补丁 v0.1.7 §F1 原文：

```text
八板块编辑（单板块全屏展开式编辑，替代桌面分栏）、审计面板（底部抽屉，可上拉半屏）
…
触屏适配原则：桌面端"拖拽调宽"全部改手势；点击目标 ≥44px；长文本编辑页全屏进入。
```

前三条的落点（`≥44px` 见 §3.4，已覆盖）：

| 桌面端形态 | 触屏形态 | 为什么 |
|---|---|---|
| 八板块**左右分栏**，同时可见多个板块 | **单板块全屏展开**，一次只看一个 | 手机宽度放不下两栏；且分栏的隐含诉求是"对照着写"，而手机上对照靠**返回时保留滚动位置**，不靠并排 |
| 审计面板**右侧常驻栏** | **底部抽屉**，可上拉半屏 | 常驻栏在竖屏里等于永久占掉 1/3 宽度；抽屉只在需要时出现，且半屏态正好能"边看审计边改" |
| 拖拽分隔条**调宽** | **单栏全屏 + 半屏抽屉**（§6.3.1，决策 #298） | 调宽的前提是"有两栏"，单栏形态下这个动作没有对应物 |
| 长文本编辑 | **全屏进入**（不在弹窗里编辑） | 键盘弹起后，弹窗里的可视区会被压到只剩两三行 |

#### 6.3.1 定案：**「拖拽调宽」→ 单栏全屏 + 半屏抽屉**（2026-10-30，决策 #298）

桌面端的拖拽调宽承载的是「**同时看着 A 写 B**」这个真实诉求，所以不是"随便换个手势"，
而是要在触屏上**用另一种方式把这个诉求兑现**。

**定案**：编辑区**单栏全屏**；需要"边看边写"时，把被参照的内容拉成**半屏抽屉**
（底部上滑半屏）。与审计面板**同一个交互、同一套展开动画**。

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| A. 单面板 + 边缘滑出 | 从屏幕边缘滑出第二个面板（覆盖式） | 与「左缘 20px 起手 = 返回」冲突（§6 / 决策 #271） | ✗ |
| B. 上下分屏 + 可调比例 | 竖屏分成上下两块，中间拖拽 | 竖屏上下分屏后每块都太矮，长文本编辑几乎不可用 | ✗ |
| C. 单栏 + 快速跳转 | 一次只显示一个，用 Tab/手势切换，切换时保留对方的滚动位置与光标 | **切走即丢上下文** —— 用户要的是"边看边写"，切换法把"看"和"写"变成串行 | ✗ 单独用 |
| **D. 半屏抽屉** | 被参照的内容放半屏抽屉，编辑区占上方 | 半屏时编辑区仍偏小 | **✓ 采用**（并吸收 C 的状态保留要求） |

**为什么是 D 而不是 C**：C 的代价不是"少看一点"，而是**把并行的动作变成串行的**。
写一段需要对照参考的内容时，人会反复"看一眼→写一句→再看一眼"；
每次切换都要重新定位（哪怕滚动位置保住了，视线也要重走一遍）。
D 的半屏抽屉让"看"始终在视野里，编辑区虽然矮一点，但**不需要来回切**。

**为什么"与审计面板同一交互"这条很重要**：用户只需要学一次"底部上滑 = 半屏抽屉"。
如果编辑页用一套、审计面板用另一套，两个都是低频操作、两套都要学，
成本是叠加的而不是分摊的。

抽屉的两种高度：**半屏**（上滑一次）与**近全屏**（上滑两次）。
半屏是"边看边写"的默认档；近全屏用于"只想看审计结果"的场景。
**不做**任意高度拖拽 —— 触屏上拖到一半停住很难精确，而两个吸附档位覆盖了真实用法。

> **判据**（实现时逐条验）：
> 1. 从面板内起手与从屏幕左缘起手（返回）两条轨迹不冲突（同 §6 对 swipe 的要求）；
> 2. 抽屉开合不丢编辑区的滚动位置与光标；抽屉自己的滚动位置也要保住；
> 3. 键盘弹起后，**编辑区仍 ≥ 屏幕高度 40%**（半屏抽屉 + 键盘同时在场时，
>    优先压抽屉而不是压编辑区 —— 用户此刻在打字，不是在读审计）；
> 4. 抽屉把手点击目标 ≥ 44px（含热区），不是只有那 4px 的视觉条。

## 7. 关键组件规范

### 7.1 消息气泡

| 属性 | 角色消息 | 用户消息 |
|---|---|---|
| 背景 | `--nb-surface-1` + 玻璃 | `--nb-grad-soft` |
| 圆角 | `20px 20px 20px 6px` | `20px 20px 6px 20px` |
| 最大宽度 | `82%` | `82%` |
| 内边距 | `12px 16px` | 同 |
| 正文 | `--nb-fs-16` / `--nb-text-1` / 行高 1.6 | 同 |

生成中：末尾一个 8px 圆点，`--nb-grad-primary`，`opacity` 在 0.3 与 1 之间呼吸（1.2s）。

### 7.2 输入区（含语音）

```text
┌──────────────────────────────────┐
│ [＋]  ┌────────────────┐  [🎤] [↑] │
│      │ 说点什么…        │          │
└──────────────────────────────────┘
```

- 输入框圆角 pill，`--nb-surface-2`，聚焦时边框转 `--nb-nebula-a`（1px，不发光）；
- 麦克风：**按住说话**。按下时全屏浮起一层半透明 + 中央波形（渐变），松手即发送识别；
- 未配置 ASR 时麦克风**置灰**（`--nb-text-3`），点击弹引导去配置页 —— 不是静默无响应；
- 键盘弹起时输入区跟随上移，Tab 隐藏（`visualViewport` 监听，不用 `resize`，
  后者在 Android 上因键盘动画会抖）。

### 7.3 空状态

每个 Tab 的空状态都要有：一句人话 + 一个明确的下一步动作。
不许出现"暂无数据"。例：

```text
        （渐变光晕 + 图标）

      还没有角色卡
   从仓库拉一张，或者新建一张

      [ 新建卡片 ]  [ 去仓库 ]
```

## 8. 面板主题接口（留给未来反哺桌面端）

需求文档要求"高亮与主题系统留'面板主题'接口供未来反哺桌面端暗色方案"。
做法：把色彩层抽象成**一层可替换的 token 映射**，而不是散落的变量。

```ts
export interface NebulaTheme {
  id: string;                 // 'nebula-night'
  name: string;               // 显示名
  tokens: Record<string, string>;  // 覆盖 --nb-* 的子集
}
```

- 内置主题只有一个：`nebula-night`（本册）。
- 用户自定义主题 = 一份 `tokens` 覆盖（存 `config.json`，不进仓库）。
- **桌面端要复用**：桌面端的暗色方案只需提供一份 `tokens` 映射，
  不需要复制任何组件代码 —— 这是"接口"而不是"移植"的关键区别。

变量命名刻意用 `--nb-` 前缀（nebula），不与桌面端既有的 `--panel`/`--border`
冲突，两套 token 可以在同一份 CSS 里共存（壳内共存场景，见需求文档 §二）。

## 9. 走查清单（每次交付前逐条过）

1. 有没有裸色值？（`grep -nE '#[0-9a-fA-F]{3,6}' src/**/*.css` 应只在 token 文件里命中）
2. 所有可点元素热区 ≥ 44px？
3. 屏幕上同时存在的玻璃层 ≤ 3？
4. 正文最小字号 ≥ 16？（列表副标题可 14，但正文不行）
5. 有没有用纯黑 `#000` 做背景？
6. 动效只动 transform/opacity？有 `prefers-reduced-motion` 兜底？
7. 空状态是不是"暂无数据"？
8. 键盘弹起后，输入框是否被挡？
9. 深色下对比度：正文 ≥ 12:1、次要 ≥ 5:1？
10. 文案里有没有内部术语？（沿用 v0.1.6 的 `verify-ui-copy` 纪律，需扩展到移动端源码）

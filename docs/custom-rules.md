# 自定义规则与预设编写指南

> 这份文档是「规则 / 预设」的完整规范。README 里只保留"可以自定义"这件事本身，
> 具体怎么写在这里。文件都是 JSON，**改错了不会崩，只会静默不生效** ——
> 所以下面每一节都写了"配错时你会看到什么"。

---

## 六类文件，各管一件事

| 文件 | 管什么 | 配错的典型症状 |
|---|---|---|
| **平台规则** | 审计：什么算错、错在哪一块、多严重 | 该报的没报；或报了看不懂的错 |
| **高亮方案** | 编辑器里哪些字上什么色 | 一片灰，或满屏同色 |
| **TXT 预设** | 八板块的标题写法、别名、顺序 | 导入时"认不出板块"，内容跑到别的块 |
| **世界书格式预设** | 世界书 TXT 的条目语法 | 条目解析不出来，或字段丢一半 |
| **初始场景格式预设** | 开场白/情景两段的段标题与多条分隔 | 规则要的标签行怎么都出不来 |
| **对话示例格式预设** | 说话人写法（`{{user}}:` ↔ `用户：`） | 板块里一直是 `{{user}}:`，规则报"缺说话人行" |

**前两类是"读的时候怎么判"，后四类是"写的时候怎么排版"。**

这两类混了会白费功夫：把版式要求写进平台规则，它只能在审查阶段报错，
**不会帮你把文本改成那个样子**；反过来，排版预设也不会替你判断对错。

### 导入之后会不会立刻生效

| 预设 | 导入后 | 为什么 |
|---|---|---|
| 初始场景格式 | **立刻启用** | 导入它的意图就是用它 |
| 对话示例格式 | **立刻启用** | 同上 |
| TXT 预设 / 世界书格式 / 平台规则 / 高亮方案 | 只是加进候选，需要在下拉里选中 | 这四类会改变导出与解析口径，静默切走风险更大 |

前两类导入后面板会提示「已设为当前使用」。如果**只提示"导入成功"而没有这半句**，
说明装的是旧版客户端（2026-11-17 之前），那种版本导入预设后**一个字都不会生效** ——
必须再去下拉里手选一次，或者升级。

已生效的预设会记住，下次打开还是它；文件本身存在应用配置目录的
`preset-library.json` 里，**改磁盘上的原始 JSON 不会自动跟上**（那只是导入源）。

## 平台规则

```json
{
  "schemaVersion": 1,
  "id": "my-platform",
  "name": "我的平台",
  "version": "1.0.0",
  "description": "这份规则要求什么、为什么",
  "extends": "sillytavern",
  "target": { "spec": "any" },
  "placeholders": {
    "char": ["{{char}}"],
    "user": ["{{user}}"]
  },
  "fields": [
    {
      "path": "meta.name",
      "label": "角色名",
      "required": true,
      "minLength": 1,
      "maxLength": 64,
      "severity": "error",
      "message": "角色名不能为空"
    }
  ],
  "rules": [
    {
      "id": "char-at-least-1",
      "type": "placeholder-min-count",
      "token": "char",
      "min": 1,
      "scope": ["block:basic", "block:personality"],
      "severity": "warning",
      "message": "这段没有用到 {{char}}",
      "hint": "把角色名换成 {{char}}，换角色时不用全文改"
    }
  ],
  "autoFix": []
}
```

**顶层字段**：`schemaVersion` / `id` / `name` / `version` / `description` /  
`extends` / `target` / `placeholders` / `fields` / `rules` / `autoFix` / `metadata`。

- `extends`：父规则 id。先应用父规则，再用本文件**同名 id** 的规则覆盖它；  
  `fields` 与 `autoFix` 按 id / type 追加。想"只加一条限制"就继承，别整份复制。
- `placeholders`：声明平台认哪些占位符写法。写在 `char` 下的每种写法都算合法，  
  校验时合并计数。
- `fields`：字段级检查。`path` 用点号路径（`meta.name`、`description`、`first_mes`），  
  配 `required` / `minLength` / `maxLength` / `severity` / `message`。

**`rules[]` 的 7 种 type**：

所有规则都要 `id`（文件内唯一）、`type`、`message`、`scope`、`severity`，  
可选 `hint`、`enabled`。

| type                    | 专属字段                                   | 判定                                                    | 典型用途               |
| ----------------------- | -------------------------------------- | ----------------------------------------------------- | ------------------ |
| `placeholder-min-count` | `token`、`min`、`max?`、`aggregate?`      | 统计该占位符所有合法写法的出现次数，越界即报                                | 强制出现 `{{char}}`    |
| `placeholder-forbid`    | `token`                                | 出现任意合法写法即报                                            | 某平台禁用某占位符          |
| `pattern-forbid`        | `pattern`、`flags?`                     | 正则命中即报，报错带命中片段                                        | 禁止 `<BOT>`、禁止 HTML |
| `pattern-required`      | `pattern`、`flags?`、`min?`、`aggregate?` | 命中次数不足 `min`（默认 1）即报                                  | 示例对话必须有 `<START>`  |
| `length`                | `min?`、`max?`、`unit?`                  | 计数越界即报；`unit: "char"`（默认，不含空白）或 `"word"`（拉丁词 + CJK 字） | 描述过短、开场白超长         |
| `non-empty`             | —                                      | 去掉空白后为空即报                                             | 板块必填               |
| `forbidden-words`       | `words`、`caseSensitive?`               | 命中词表任一词即报（字面量，不是正则）                                   | 平台禁用词              |

**`scope` 选择器**决定检查哪些文字：`block:basic` / `block:personality` /  
`block:settings` / `block:special` / `block:user` / `block:chat-examples` /  
`block:initial-scene` / `block:worldbook`，可用 `field:meta.name` 这类字段选择器，  
也可写 `card` 表示全文。

默认是**逐个检查**：`scope: ["block:basic","block:settings"]` 表示每个板块各自都要满足，  
报错能精确到板块与行。需要"全文合计"时加 `"aggregate": true`，把各段拼起来统计一次。

```json
{
  "id": "char-twice-in-card",
  "type": "placeholder-min-count",
  "token": "char",
  "min": 2,
  "aggregate": true,
  "scope": ["block:basic", "block:special"],
  "severity": "error",
  "message": "全文至少出现 2 次 {{char}}"
}
```

**「初始场景」「对话示例」默认只做格式检查。** 这两块的**内容**没有客观标准  
（开场白多长算合适？示例对话该几轮？），所以内容规则波及它们时默认不检查。  
愿意为这个判断负责的规则作者，显式写 `"contentOptIn": true` 才生效：

```json
{
  "id": "mine:example-needs-start",
  "type": "pattern-required",
  "pattern": "^<START>\\s*$",
  "flags": "gm",
  "scope": ["block:chat-examples"],
  "contentOptIn": true,
  "severity": "warning",
  "message": "示例对话缺少 <START> 分段标记"
}
```


挡的粒度是**每段文本**，不是整条规则：`scope: "*"` 的规则不会因为波及这两块就整体  
失效，basic / settings 该报的照报。点名 `field:first_mes` / `field:mes_example` 的写法  
本身就是显式声明，不受这条边界影响；格式类检查（分隔行二义、旧六板块卡、世界书条目  
结构…）走的是另一条路径，也照常。`contentOptIn` 只接受布尔值，写 `"true"` 会直接报错。

**严重级决定要不要拦导出**：`error` 导出前弹窗确认；`warning` 只提醒；  
`info` 折叠展示。

**`autoFix[]`** 用于平台切换时自动适配文本：`replace-text`（`from`/`to`/`caseSensitive?`，  
字面量替换）、`replace-regex`（`pattern`/`flags?`/`replacement`，支持 `$1`）、  
`trim`（去首尾空白与多余空行）。

## 从别的平台搬来的卡，怎么写才对

如果你是从别的平台（或别的工具）搬卡过来的，**对话示例**与**开场白**这两处最容易
"看起来正常、其实读不到"。下面是逐条对照，每条都对应一条能查到的规则 id。

### 对话示例（`mes_example`）

| 常见写法 | 该怎么写 | 不改的后果 | 对应规则 |
|---|---|---|---|
| `用户：…` / `角色：…` | `{{user}}: …` / `{{char}}: …` | **整块被读卡方静默丢弃** | `example-speaker-halfwidth-colon` |
| `{{char}}：…`（全角冒号） | `{{char}}: …`（半角冒号） | 匹配不到说话人，同样整块丢 | `example-macro-halfwidth-colon` |
| 用 `===` / 空行分段 | 每段开头单独一行 `<START>` | 只有第一段有效 | `example-uses-start-marker` |
| 第一行直接写正文 | 第一行必须是 `<START>` | 第一行会被当成"说明行"跳过 | `example-uses-start-marker` |

**最反直觉的一条是最后一行**：读卡时**块内第 0 行会被无条件跳过**，所以
`<START>` 必须独占那一行，正文从第二行开始。少了这一行，那段示例的第一句就没了。

正确样子：

```text
<START>
{{user}}: （把已经放凉的咖啡推过去）"你又放凉了，先喝一口。"
{{char}}: （瞥了一眼杯子）"少管我……杯子给我。"
<START>
{{user}}: （扶着受伤的学员坐下）"他的膝盖旧伤复发了。"
{{char}}: （接过记录，蹲下检查）"护膝和冰袋拿来。"
```

### 开场白（`first_mes`）

| 情况 | 该怎么处理 | 对应规则 |
|---|---|---|
| 一条都没有 | 至少写一段；想给多个开局用「备用开场白」 | `first-mes-not-empty` |
| 想给多个开局 | 第一段放开场白，其余放备用开场白 | — |

开场白**不进上下文**，它的作用是"新对话的第一条消息"。所以它写得再长也不花
每轮的额度；反过来，空着的话开始聊天就是一片空白。

### 场景（`scenario`）与开场白要一致

`scenario` **每轮都会发给模型**，而开场白是第一条消息。两者说的必须是同一个地方：

```text
scenario    "旧城区下着小雨，{{user}}推门走进「拾光」书店"      ← 每轮都在发
first_mes   "夜里十点半，私人健身工作室…"                        ← 聊天从这里开始
```

上面这两句来自两张不同的设定。模型每轮看到的是"书店"，而对话发生在"健身房"。
表现就是"AI 老是把场景搞错"，但改提示词怎么改都没用。
在「卡片 → 开场与示例」里这两段是**同一屏**，一眼就能看出来。

### 为什么这些规则现在才出现

`rules/platforms/sillytavern.json` 原来只检查占位符，**完全没有管对话示例**。
而 `character-card-v3` / `chub` 那两份规则包反而有 `<START>` 检查。
如果你用「SillyTavern」这份规则审计，上面这些问题一条都不会提示。
现在补上了，严重级统一是 `warning`：**只提醒，不拦导出**（存量卡本来就长这样，
直接拦下来会让人卡在"改不完就发不出去"里）。

## 高亮方案

```json
{
  "schemaVersion": 1,
  "id": "my-theme",
  "name": "我的配色",
  "version": "1.0.0",
  "extends": "default",
  "theme": { "foreground": "#222222", "background": "#ffffff" },
  "scopes": [
    { "id": "heading", "label": "板块标题", "color": "#1f4e79", "bold": true },
    { "id": "placeholder", "label": "占位符", "color": "#b0341b", "backgroundColor": "#fdece7" }
  ],
  "rules": [
    {
      "id": "block-heading",
      "scope": "heading",
      "priority": 100,
      "match": { "type": "regex", "pattern": "^【[^】\\n]{1,30}】\\s*$", "flags": "gm", "wholeLine": true }
    },
    {
      "id": "char-placeholder",
      "scope": "placeholder",
      "priority": 90,
      "match": { "type": "delimiter-block", "open": "{{", "close": "}}" }
    }
  ]
}
```

- `scopes[]` 定义样式（`id` / `label` / `color` / `backgroundColor` / `bold` / `italic` 等）。
- `rules[].match` 有**四种匹配方式**：

| `match.type`      | 专属字段                                   | 行为                                        |
| ----------------- | -------------------------------------- | ----------------------------------------- |
| `regex`           | `pattern`、`flags`（`gimsu`）、`wholeLine` | JS 正则；`wholeLine: true` 把命中扩展到整行，适合标题与分隔线 |
| `word-list`       | `words`、`caseSensitive`、`wholeWord`    | 关键字字面量匹配，自动转义元字符，无需自己转义                   |
| `line-prefix`     | `prefix`                               | 行首标记（如 `"## "`），只着色前缀本身                   |
| `delimiter-block` | `open`、`close`、`escape?`               | 成对分隔符内的整段，如 `{{`…`}}`；未闭合时不报错，匹配到行尾       |

「成对符号包裹」的场景优先用 `delimiter-block`，不用跟正则转义较劲。

- **`appliesTo` 把规则限定到某些板块**（可选）：`"*"` / `"block:<板块 id>"` / `"field:<ST 字段名>"`，  
  可以是数组（任一命中即生效）；不写就是**全部板块**。`block:` 的 id 与上一节 `scope` 那 8 个相同。  
  两个容易踩的点：① 这是**逐板块过滤**，不是"换一套规则"，同一段文字照样可能被多条规则命中，
    
  按下面的优先级裁决即可；② **不写 `appliesTo` 就等于"哪儿都管"**，内置的 `hr-line` 会命中
    
  初始场景里的 `---`，不是因为它点名了这个板块，而是因为它哪儿都管。同一种符号在不同板块
    
  保持同一种颜色是刻意的，所以初始场景专用的 `scene-divider` 用更低的优先级，只负责补上
    
  `hr-line` 不认识的写法（`~~~`）。
- `enabled: false` 临时关掉一条规则，编译期直接剔除，不用删代码也不用注释掉。
- **冲突消解**（同一段文字被多条规则命中时）：先比 `priority`（大者胜）→ 再比命中长度  
  （长者胜）→ 仍是平手就看**声明顺序**（数组靠前者胜）→ 最后以起始偏移兜底。  
  这条链是写死的：同一份规则 + 同一段文本，永远得到同一组着色区间。  
  想让某条规则赢，把它写靠前或提 `priority`，不要依赖巧合。
- 已被高优先级规则占用的部分**只让出那一小段**，不会吞掉整条低优先级匹配。

内置 `default` 方案带 7 条板块专用规则：世界书 5 条（条目开 / 闭标记、正文标记、
  
触发键行、条目名行）、对话示例 1 条（`<START>` 分段标记）、初始场景 1 条（分隔行）。
  
`dark` 写了 `extends: "default"`，所以同样继承这 7 条；`minimal` 不继承（`extends: null`），
  
换过去就没有这层配色了。这不影响正确性，只是"看起来朴素"。

**注意一处耦合**：标题规则里的 `【…】` 来自默认预设的 `headings.*.pattern`。  
换成 `## 标题` 的预设后，标题高亮会**静默失效**（不报错，只是不着色），  
需要同步改这条正则。

## TXT 预设（板块标题、别名、顺序）

```json
{
  "schemaVersion": 1,
  "id": "my-preset",
  "name": "我的预设",
  "version": "1.0.0",
  "blockOrder": ["basic", "personality", "settings", "special", "user", "chat-examples", "initial-scene", "worldbook"],
  "headings": {
    "basic": {
      "pattern": "【{title}】",
      "aliases": ["基本信息", "基本资料", "角色信息"]
    },
    "personality": { "pattern": "【{title}】", "aliases": ["性格", "性格设定"] },
    "settings": { "pattern": "【{title}】", "aliases": ["其他设定", "其它设定"] },
    "special": { "pattern": "【{title}】", "aliases": ["特殊设定", "特别设定"] },
    "user": { "pattern": "【{title}】", "aliases": ["用户相关设定", "用户设定"] },
    "chat-examples": { "pattern": "【{title}】", "aliases": ["对话示例", "示例对话", "对话范例"] },
    "initial-scene": { "pattern": "【{title}】", "aliases": ["初始场景", "开场场景", "开场白"] },
    "worldbook": { "pattern": "【{title}】", "aliases": ["世界书", "世界设定"] }
  },
  "separator": "\n\n",
  "greeting": { "separator": "\n\n---\n\n" },
  "worldbook": { "includeHeading": true }
}
```

| 字段                         | 含义                                                                        |
| -------------------------- | ------------------------------------------------------------------------- |
| `blockOrder`               | 板块顺序（导出按它排，**只有"应用预设"才会重排现有文本**）。缺项会自动补齐并提示，旧预设不用改                        |
| `headings.<block>.pattern` | 标题模板，`{title}` 会被替换成板块名                                                   |
| `headings.<block>.aliases` | 解析时认哪些标题写法，用于归一化比对（繁体、缩写都放这里）                                             |
| `separator`                | 板块之间的分隔符，默认空行                                                             |
| `greeting.separator`       | 多条开场白之间的分隔串（旧写法）。现在**推荐用「初始场景预设」**，见 [4.3c](#43c-字段板块预设)；两者都在时以"值不同"决定谁生效 |
| `worldbook.includeHeading` | 世界书段是否带标题行                                                                |

改标题文案是允许的：解析走别名表归一化，导出沿用你改后的标题；  
「应用预设」只换装饰符、保留标题文字。

预设可以**导入导出**：「规则与预设 → TXT 预设」有「导入预设文件… / 导出当前预设…」。
  
导入走 schema 校验，坏文件不会动你现有的列表；同 `id` 会覆盖。导入后**不会**自动
  
切换过去，要自己在下拉里选。

## 世界书格式预设

世界书的 TXT 格式也可以换。内置的「标准世界书」就是冻结的 v1.0
  
（`@@ENTRY 0` / `@@CONTENT` / `@@END 0`），导出与它**逐字节一致**；
  
你可以在「规则与预设 → 世界书预设」里导入自己的格式，把标记、字段标签、
  
字段顺序、分隔符都改掉：

```json
{
  "schemaVersion": 1,
  "id": "cn-kv",
  "name": "中文键值世界书",
  "version": "1.0.0",
  "format": {
    "entryOpen": "条目{id}：",
    "contentMark": "内容：",
    "entryClose": "条目{id}结束",
    "fieldOrder": ["name", "keys", "insertion_order"],
    "labelMap": { "name": "名称", "keys": "关键词", "insertion_order": "触发深度" },
    "fieldSeparator": ["：", ": ", ":"],
    "listSeparator": "、",
    "entrySeparator": "\n"
  }
}
```

- 三个标记都必须含 `{id}`（正文标记除外），且互不相同；
- `labelMap` 把字段名换成你文件里的标签，解析时按它反查；
- 世界书的**导出、导入、格式检查**都按当前选中的预设走：三处必须同一份，
    
  否则会出现"导出用 A 格式、检查按 B 格式"的错位；
- 切换预设不会改你已有的世界书内容，只改变"下次导出/读取时按哪种格式解析"。
- **卡片的写法与当前预设不同时会自动重排**（v0.1.6）：从服务器取回、打开本地文件、
    
  导入 TXT 这三条路进来时，工具先用**当前预设**去读；读不通就用**标准写法**再读一次。
    
  能读通说明卡本身是好的、只是写法不同，于是按你当前预设重新排版，状态栏给一条
    
  **提示**（「世界书原为…，已按当前预设…重新排版」），条目一条不丢、导出照常。
    
  两种写法都读不通才算**真的解析不出**，那时才报错并挡住导出（避免把内容写空）。
    
  这条修的是"标准格式的卡 + 自定义预设 ⇒ 报世界书格式错误"那个误报。
- `listSeparator` 可以是**数组**（v0.1.5）：写成 `[", ", "、", "，"]` 就同时认
    
  半角逗号、顿号、全角逗号。写回时只用第一个，保证输出唯一。
    
  你的关键词行混用顿号与逗号时，这一项就不用挑边站了。
- `fieldSeparator` 同样**可以是数组**（2026-11-17）：写成 `["：", ": ", ":"]` 就同时认
  全角与半角冒号。中文标签用全角、从 ST 抄来的字段名用半角时，只给一种会让另一半
  行整行丢弃（详见文末「实战：三处最常见的方言问题」第 ③ 条）。
  规则是：**第一个用于写出**（输出必须唯一），全部用于解析，且解析时按
  "位置靠前 + 标签能识别"挑 —— `comment: 备注：补充` 这种值里带全角的不会被切错。

### 布尔字段可以写成中文（`常驻：是`）

`constant`（常驻）这类布尔字段，`labelMap` 登记后可以写中文值：

```json
"labelMap": { "name": "名称", "keys": "关键词", "constant": "常驻" }
```

条目里就能写 `常驻：是`。**认的值**：`是 / 否`、`true / false`、`1 / 0`
  
（英文大小写不敏感，另外 `yes/no/on/off` 也认）。

`真/假`、`对/错`、`√/×` **不认**：认不出时不猜，只报一条
  
`bad-value` 提示并让该字段保持缺省（`constant` 即按 `false` 处理）。
  
这条是刻意的：`常驻：假` 若被猜成 `true`，条目会变成常驻而你以为它是关键词条目。

> ⚠ 想让 `常驻：是` 在**导出的 TXT** 里也写回去，还要把 `constant` 加进
>   
> `fieldOrder`。`fieldOrder` 是白名单，没列的字段不会写出（JSON 导出不受影响，
>   
> `character_book.entries` 带全部字段）。

### 标记可以"粘连"内容（v0.1.5）

很多外部世界书的写法是把名字或正文直接接在标记后面，而不是另起一行：

```
【条目1：西奥核心关系逻辑】     ← 名字和标记在同一行
顺序：275
内容：{{char}}与{{user}}…      ← 正文和"内容："在同一行
```

这两种都能**直接解析**，不需要改你的文本：

- `entryOpen` 后面多出来的内容按**条目名**处理，并自动去掉配对的收尾符号
    
  （`】`、`]`、`）` 等）。名字内部的括号不动。`设定（草稿）` 的括号是名字的一部分；
- `contentMark` 后面多出来的内容算**正文第一行**。

所以 `"entryOpen": "【条目{id}："` 配 `"contentMark": "内容："` 就能吃下上面那种写法。

**触发条件**是标记模板在 `{id}` 之后还有字符（如 `：`、`】`、`>`）。那种收尾符
  
天然标记了"名字到哪结束"。反过来，内置的 `@@ENTRY {id}` 没有收尾符，
  
**仍然要求标记独占整行**，后面的内容不会被当成名字。

两条补充：

- 行内名称是**兜底**：如果条目里另有 `名称：xxx` 这样的字段行，字段行说了算
    
  （显式字段比猜测可信）。前提是该标签在预设的 `labelMap` 里登记过。
    
  没登记的话那一行会被当成「未知字段」忽略并提示，行内名继续生效；
- 正文标记在条目内**只认一次**（它表示"正文从这里开始"）。

### 结束标记可以不要（隐式闭合）

`entryClose` 允许**留空**，含义是"条目由下一个开标记或文件结束来分界"。
  
标题式世界书（`【条目1：xxx】` 一路排下来）本来就是这么写的。

- 留空 = 永远按隐式闭合解析，不报任何问题；
- 写了但整份文本**一次都没用到** → 按隐式闭合解析，并给一条提示
    
  （"你的写法本来就是隐式闭合的话，把 entryClose 留空即可不再提示"）。
    
  这条**只对你自己导入的预设生效**；
- 写了、且**有的条目用了有的没用** → 报错指出是哪个条目缺结束行。
    
  那是真的写漏了，不能替你掩盖。

反过来，内置「标准世界书」的 `@@END {id}` **永远严格**：少写就报错，不会被
  
"自动当成隐式闭合"放过。那是本工具写出去的格式，缺就是缺。

### 重复 id：内置严格，自定义预设续号

同一个 `id` 出现两次时，两种格式的行为不同：

| 当前格式      | 行为                                                                           |
| --------- | ---------------------------------------------------------------------------- |
| 内置「标准世界书」 | 报 **error**，拒绝写回（不动你原有条目）。手写两个 `@@ENTRY 3` 可能是"想改前一个"也可能是"想覆盖"，替你选一种就是替你改了数据 |
| 你自己导入的预设  | 按出现顺序**自动续号**（取当前最大 id + 1）并提示「已重新编号为 N，两条内容都保留」                             |

为什么分档：外部世界书常按小节各自从 1 编号（"持续世界书"1–7 条、
  
"关键词世界书"1–12 条），合起来必然撞号。单看每节都合法，报 error 会让整份
  
几千字无法写回。又变成"静默丢内容"。而内置格式是你手写的规范文本，
  
撞号就是写错了。

这条边界适用于三处放宽：隐式闭合、重复 id 续号、`listSeparator` 回退。
  
**内置格式永远按规范严格校验**，只有你自己导入的预设才享受容错。否则
  
"合法的输入行为悄悄变了"，比"不合规的输入被拒"难发现得多。

### 世界书不会被"静默导丢"

如果你把别的工具格式的世界书粘进面板（比如 `【条目1：xxx】` + `顺序：` + `内容：`），
  
本工具**认不出来**。它要的是 `@@ENTRY` / `@@CONTENT` / `@@END` 三个标记。
  
这种情况下：

- 面板会明确报错并说出检测到的外来格式，**不会**把原有条目清空；
- 导出会被**硬阻止**（导出按钮变灰），提示
    
  「世界书条目未能解析，导出将丢失内容，请先修复格式」。

这条拦截**不提供"仍要导出"**。因为绕过等于同意丢掉那几千字，
  
而你在编辑器里看着内容还在，不会意识到会丢。修好格式后按钮自动恢复。
  
（v0.1.4 及更早没有这道防线，会静默导出空世界书。）

**格式与内容是两条轨**：上面这套参数只管"怎么写"；"写什么"（条目名必填、
  
关键词至少几个、触发深度范围）归平台规则管，见 [4.5](#45-给世界书条目加自己的校验规则)。
  
内置只覆盖标准平台规范。你自己的约定一律走导入，不会被内置成对所有用户生效。

## 初始场景与对话示例预设

「初始场景」和「对话示例」各自落在 ST 的独立字段上：

| 板块 | 内部子段 | 落到 ST 字段 |
| --- | --- | --- |
| 初始场景 | `@@开场白` | `first_mes`（多条时其余进 `alternate_greetings[]`） |
| 初始场景 | `@@情景` | `scenario` |
| 对话示例 | 整段 | `mes_example` |

**初始场景为什么是复合板块**（v0.1.7 起）：这三样在 ST 里本来就是三个字段，
分成三个板块编辑会让"开场白和情景对不上"变成常态——写开场白时看不到情景，
写情景时又忘了开场白讲到哪。放在一个板块里、用 `@@` 分两段，改的时候能一起看。

`@@` 这个记号不是新发明的：世界书里早就用 `@@ENTRY` / `@@CONTENT` 表示
"这是结构标记，不是正文"。同一份 TXT 里不该出现两套标记体系。

**旧 TXT 怎么读**（这条最要紧，历史文件不能错位）：

```text
一个 @@ 标记都没有        → 整段当开场白（再按分隔行切多条），情景留空
有 @@开场白 / @@情景      → 各归各位
遇到旧版的【对话示例】标题 → 当作对话示例段，不报"未识别板块"
```

也就是说：**v0.1.7 之前导出的 TXT 不用改一个字**，重新导入后开场白还在原来的位置。

至于"一段文本怎么写"——分隔行用 `---` 还是 `===`、段落要不要带 `【开场白】`
这类标签行——那是**格式**，所以和 TXT 预设、世界书预设一样可以换。
两块各有一份预设，在「规则与预设 → 初始场景预设 / 对话示例预设」。

```json
{
  "schemaVersion": 1,
  "id": "my-greeting",
  "name": "我的开场白格式",
  "version": "1.0.0",
  "block": "initial-scene",
  "format": {
    "separator": "\n\n===\n\n",
    "labelMap": { "first": "【开场白】", "alternate": "【备用 {n}】" }
  }
}
```

| 字段                 | 含义                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------- |
| `block`            | 这份预设只能用在哪块：`initial-scene` 或 `chat-examples`。**导错栏会被拒**（把对话示例预设导进初始场景那栏不会静默生效）        |
| `format.separator` | 初始场景：多条开场白之间的分隔串；对话示例：**轮次分隔**，只用于统计轮数与审计文案，**不改写正文**                                 |
| `format.labelMap`  | 初始场景：`first`（第一条）、`alternate`（备用，支持 `{n}` 占位符）；对话示例：`turn`（轮次的称呼）。**空对象 = 不写标签也不认标签** |

校验口径（任何一条不满足都**拒绝导入并指出原因**，不会"存进去但不生效"）：

- 初始场景的 `separator` 不能为空、必须含换行，且**必须有一行非空文字当识别标记**
    
  （`---`、`===` 之类）。纯空行分隔会被拒。那样分不清"换页"和"段落间距"；
- 对话示例的 `separator` 可以是空串，含义是"不切分"（内置默认就是这样）；
- 标签不能含换行、不能与分隔识别标记同形、两个角色不能共用同一个标签。这三条都会
    
  让反解出现二义。

**现在生效的是哪一份**（初始场景，按优先级）：

1. 你在下拉里选的**自定义**初始场景预设。它说了算；
2. 否则 TXT 预设显式写了 `greeting.separator`、且值与当前不同，用它。这条是兼容
     
   v0.1.3 早期写法的：那时分隔符只存在于 TXT 预设里，忽略它等于"用户设过的值不见了"；
3. 否则用冻结默认：空行 + `---` + 空行，不写标签。

面板会把来源如实写在下面一行（「来自冻结默认」/「来自上选的预设」/「来自 TXT 预设的
  
`greeting.separator`（旧写法）」），不需要你猜为什么换的预设"没起作用"。

内置两份都**冻结**，等价于 v0.1.3 已发布的行为：`标准初始场景`（空行 + `---` + 空行切分，
  
不写标签，导出与它逐字节一致）、`标准对话示例`（整段保存，不切分轮次）。导入导出、
  
同 `id` 覆盖、导入后不自动切换、坏文件不动现有列表：与世界书预设同一套规则。
  
**换预设不改已有正文**，只改变"下次导出用哪种分隔行""接下来怎么读"。


最后一条边界：这里只管**格式**。开场白写得好不好、示例对话该几轮，本工具不评价。
那属于内容，规则作者若要管必须显式 `contentOptIn`（见 [4.1](#41-平台规则)）。

## TXT 导入的问题分级

口径只有一条：**导入不因为「板块不全」而失败**。认出多少算多少，剩下的原文一律进
【其他设定】（见 [4b](#4b-导入-txt原文一个字都不会丢)）。真正的 `error` 只剩一类。
世界书段自身的结构错误。

| 情况 | 导入时会发生什么 |
| --- | --- |
| 一个板块标题都没认出来 | **不报错**。原文逐字节放进【其他设定】，对话框与状态栏说明「未识别到任何板块，原文已整体放入【其他设定】，请自行分块」 |
| 只认出部分板块 | **不报错**。认出的正常填入；未识别的片段（标题行 + 正文作为整体）按原序放进【其他设定】，前面一行分隔符。没被认出的板块在编辑器里仍标「原文缺失」。那只是提示，不拦导入 |
| 标题重复 | **警告**。内容归入首次出现的那个板块，不丢、不猜 |
| 标题认不出但写法接近 | **警告** + 最接近板块的猜测（如 `世界書` → `世界书`），原文照样保全 |
| 有内容被保全进【其他设定】 | **提示性警告**（`unrecognized-preserved`）：「识别到 N 个板块，另有 M 段未识别内容已按原序放入【其他设定】」，只是告知，不是错误 |
| 世界书段有结构性错误（`@@ENTRY` / `@@CONTENT` 不配对等） | **错误，中止**。原卡片一个字节都不改，导入失败后你的卡还是导入前那张 |

导入对话框里的「严格 / 宽松」两个单选**在当前版本结果完全相同**（连问题列表都一样）。
保全机制优先于缺板块语义，选哪个都不会因为缺板块中止。保留它们只为兼容旧习惯与旧预设说明。

> 编辑器**保存**不走保全：我们自己渲染出来的 TXT 一定八板块标题齐全，若那里也套保全，
> 你手删一个标题再保存就会被自动补一段分隔符进【其他设定】。那不是保全，是自作主张。

## 给世界书条目加自己的校验规则

平台规则的 `scope` 可以指到**世界书的每个条目**，写法是
`worldbook:entries[].<字段>`（字段可选 `name` / `keys` / `secondary_keys` /
`content` / `comment` / `position` / `insertion_order` / `priority` / `depth` /
`constant` / `enabled` / `selective` / `case_sensitive`）。问题会落到具体条目上。

内置已经有一组「默认世界书规则」（6 条，全部是 SillyTavern 规范层面的判据：
关键词为空且非常驻、关键词含空项、`selective` 没次级键、`position` 取值、`insertion_order` 为负）。
你自己的约定写进导入的规则里即可，**同 `id` 覆盖内置那条、`enabled: false` 关掉它、新 `id` 追加**：

```json
{
  "id": "mine:keys-at-least-two",
  "type": "list-count",
  "min": 2,
  "message": "{entry}的关键词少于 2 个，可能触发不到",
  "scope": "worldbook:entries[].keys",
  "severity": "warning",
  "category": "worldbook"
}
```

- `{entry}` 会替换成条目名（没有名字时是「第 N 条」），`{count}` / `{value}` 同理；
- 三种类型专门为条目字段而设：`list-count`（项数）、`number-range`（数值范围）、
  `list-no-blank-items`（列表里的空项）。别用 `length`。它量的是**文本长度**，
  拿来判"关键词至少 2 个"会把 3 个单字关键词和 1 个长关键词判成一样；
- `when` 表达同一条目内的跨字段条件，如"关键词为空**且**不是常驻"：
  `"when": { "field": "constant", "notEquals": true }`；
- **`when` 还能只判字段在不在**（v0.1.5）：

  | 写法 | 含义 |
  | --- | --- |
  | `{ "field": "priority", "exists": true }` | 该字段**存在**才求值（`0` 与空串算存在） |
  | `{ "field": "priority", "absent": true }` | 该字段**不存在**才求值 |
  | `{ "field": "priority", "present": true }` | 旧写法，等价于 `exists`（保留兼容） |

  典型用途：一堆条目里只有某几类带某个字段，用它把规则**限定到那一类**。

  > ⚠ **例外：不要用 `priority`（触发概率）判断条目类型。** 这个字段在
  > SillyTavern 里是「关键词型 / 持续型都可能出现」的通用字段，不是哪一类
  > 专属的标记。用它写 `"when": { "field": "priority", "absent": true }`
  > 来判"关键词型"时，只要那份卡里所有条目都没写触发概率，规则就会对
  > **每一条**求值 —— 表现是满屏报错，而你会以为规则配错了方向。
  >
  > 判"是不是关键词型"只有一条可靠依据：**`constant`**。见下面那条。

  存在性与值条件可以一起写，**两个都要满足**才算成立。

- **判"关键词型 / 常驻型"只看 `constant`**，这也是内置那条
  「关键词为空且非常驻」用的判据：

  ```json
  "when": { "field": "constant", "notEquals": true }
  ```

  含义：`constant` 不是 `true`（含没写这个字段）的条目才算关键词型，
  才要求它有关键词。`constant: true` 的条目一条都不会被要求。

  四种组合的实际结果（`test` 里有对拍）：

  | `constant` | 关键词 | 报不报 |
  |---|---|---|
  | `false` / 没写 | 空 | **报** —— 它确实永远不会触发 |
  | `true` | 空 | 不报 —— 常驻条目按定义不需要关键词 |
  | `false` / 没写 | 有 | 不报 |
  | `true` | 有 | 不报 |

  ★ **改 `when` 不能代替改数据。** 一份 `constant: false` 且没有关键词的
  条目，上面那条规则指出的是**真问题**（导出到 ST 后它不会生效）；
  只把 `when` 改成别的字段，只会让报错条件变来变去，条目本身仍然不生效。
  要让它真的生效，就在条目里写 `constant: true`（或补上关键词）。
  若你的平台本来就把"没写关键词"当常驻，那这条规则对你的卡不成立 ——
  用 `"enabled": false` 关掉它，而不是改判据。

- 内置判据不会因为你加了自定义规则就消失；要关掉某条必须**用同一个 id 覆盖**它。
  内置的 `builtin:worldbook-no-trigger`（"没有任何关键词也不是常驻"）同样可以用
  `"id": "builtin:worldbook-no-trigger"` 覆盖并补上 `when`。

## 导入的预设会保存在本地

六类预设（平台规则、高亮方案、TXT 预设、世界书格式、初始场景格式、对话示例格式）
**导入即保存，下次打开还在**；当前选中的是哪一项也会一起记住（包括上次用的平台规则、
高亮方案、导出格式与世界书格式）。

- 保存位置：应用配置目录下的 `preset-library.json`（与配置文件同目录，Windows 一般在
  `%APPDATA%\<应用标识>\`）。
- **删掉这个文件即恢复出厂预设**：内置预设来自安装包，删掉库只是丢掉你导入的那些。
- 文件坏了不会让程序起不来：坏的那一条会被跳过并在状态栏说明是哪一条，其余照常可用；
  整份读不懂时**不会覆盖原文件**（你可以手工修，或直接删掉）。
- 同 `id` 覆盖内置那份时，**这次是永久的**。想保留内置版本就把导入文件里的 `id` 改掉。
- 保存失败（磁盘满、目录只读）会在状态栏明确说「没能保存，重启后需重新导入」，
  不会假装成功。

> 世界书格式预设尤其值得保存：它就是「`【条目{id}：` 这种外部写法」的唯一载体。
> 丢了它，同一份世界书文本下次会按标准格式解析，一个条目也认不出来。

## 实战：三处最常见的方言问题

这三条都是从真机上收回来的，共同点是**不报错、只是不生效**，所以单独列出来。

### ① 板块里还是 `{{user}}:`，规则说"缺说话人行"

缺的是对话示例预设里的两个键：

```json
"labelMap": { "turn": "回合", "user": "用户", "char": "角色" }
```

只写 `turn` 时，渲染与反解**一个字符都不会动**（这是刻意的：不动就代表"不转换"，
而不是"转换失败了"）。于是板块里保持 ST 写法，而你的规则按平台写法判 —— 必然红。

配好之后是双向的：导入把 `{{user}}:` 渲染成 `用户：`，导出把 `用户：` 还原成
`{{user}}:`。**只配一边会脏数据**，见 [从别的平台搬来的卡](#从别的平台搬来的卡怎么写才对)。

### ② 段标题一直是 `@@开场白`，规则要 `【初始场景：】`

缺的是初始场景预设里的 `greeting` / `scenario` 两个键：

```json
"labelMap": {
  "greeting": "【第一条消息：】",
  "scenario": "【初始场景：】"
}
```

`greeting` 是"开场白那一段的标题"，`scenario` 是"情景那一段的标题"。
不配就用内置默认 `@@开场白` / `@@情景` —— 那条规则永远过不了。

**别把 `greeting` 和 `first` 写成同一个值。** 两个键是不同层级：

```text
greeting  段标题        【第一条消息：】     ← 整个板块里出现一次
first     每条开场白的标签行              ← 每条开场白前面各一次
```

写成一样时那个标记会出现两次，而解析只剥第一行 —— 第二次就留在正文里了，
表现为"开场白开头多出一行字"。

### ③ 世界书字段丢一半、还凭空多出十几个语义错误

查 `fieldSeparator` 是不是只给了一种冒号。中文标签常用全角、ST 原生字段是半角：

```text
关键词：              全角
constant: false       半角
顺序: 250             半角
```

只给全角时，半角那些行**整行被丢弃**（只有一句 `unexpected-line` 警告），
于是 `constant` / `enabled` / `selective` / `comment` / `priority` 全没了：

```text
条目名 → 退化成「第 1 条」
"有没有关键词"的规则 → 按缺省值误判
→ 每一条都报"永远不会被触发"
```

正确写法是数组，第一个用于写出、全部用于解析：

```json
"fieldSeparator": ["：", ": ", ":"]
```

配套的一条：解析时若条目只有 `comment` 没有 `name`，**会用 comment 当名字**
（ST 生态里条目标题的权威字段就是 comment）。所以看到「第 N 条」就说明名字整条链路没读到。

### ④ 满屏「没有任何关键词，永远不会被触发」

先分清是**误报**还是**真问题**——这两者的修法完全不同，而且改错了会白忙一轮。

判据只有一条：**看那个条目的 `constant`**。

```text
constant: true        常驻条目，按定义不需要关键词 ⇒ 报错才是 bug
constant: false/没写   关键词型条目，而它没有关键词 ⇒ 报错说的是真话
                      （导出到 ST 后它确实不会被任何对话触发）
```

为什么容易判错：很多人用「有没有触发概率（`priority`）」来区分条目类型，
然后写 `"when": { "field": "priority", "absent": true }`。但 `priority` 在 ST 里
是**通用字段**，不是哪一类的专属标记。只要那份卡里所有条目都没写它，
规则就会对每一条求值 ⇒ 满屏报错，而你会去改判据、改预设，越改越乱。

所以：

| 你的情况 | 该做什么 |
|---|---|
| 这些条目本来就该一直生效 | 在条目里写 **`constant: true`**（这才是真修复） |
| 它们确实该按关键词触发，只是忘了写 | 补关键词 |
| 我的平台就是"没写关键词＝常驻" | 用 `"enabled": false` **关掉这条规则**（改判据没用） |

★ 三种里只有前两种能让条目在 ST 兼容平台上真的生效。第三种是接受"这张卡
不打算在 ST 里用"，那也完全合理 —— 但要知道自己选的是这个。

## 排查：症状 → 该改哪里

| 症状 | 最可能的原因 | 改哪里 |
|---|---|---|
| 板块里还是 `{{user}}:` | 对话示例预设没给 `user`/`char` | 加两个键 |
| 段标题一直是 `@@开场白` | 初始场景预设没给 `greeting`/`scenario` | 加两个键 |
| 开场白开头多出一行同样的标签 | `greeting` 与 `first` 给了同一个值 | 删掉 `first` |
| 条目名全变成「第 N 条」 | 名字只在 `comment` 里，或字段行没解析出来 | 查 `fieldSeparator` |
| 世界书字段丢一半、莫名报"没关键词" | `fieldSeparator` 只给了一种冒号 | 改成数组 |
| 满屏「没有任何关键词，永远不会被触发」 | 那些条目 `constant` 是 `false`／没写，而 `keys` 为空 | 看实战 ④：写 `constant: true` 或补关键词或关规则 |
| 改了 `when` 报错还是不变 | 改判据不改数据，报错条件只是换了个位置 | 同上 —— 判据不能代替改数据 |
| 导入 TXT 后内容跑到别的板块 | `aliases` 撞了（同一标题对上两块） | 去掉重复别名 |
| 规则写了但不生效 | `scope` 写错 / `when` 条件不成立 / `enabled: false` | 先临时去掉 `when` 试 |
| 关不掉内置判据 | 只改了 severity，没写同 id | 用 `builtin:<原名>` 作 id |
| 改了磁盘上的文件没变化 | 那份 JSON 只是导入源，改它不会同步到已导入的预设 | 面板里重新导入一次 |
| 导入成功了，但格式没变 | 装的是旧版客户端（只提示"导入成功"，没有"已设为当前使用"） | 升级，或先去下拉里手选一次 |
| 世界书整段报"没有条目标记" | 预设的三个标记与文本不符 | 按报错里的"检测到…写法"逐项对 |

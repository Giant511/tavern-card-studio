## 0. 一句话

把已经在真机上跑通的「`libnode.so` + ST 1.19」搬进一个 Android 应用，
用**前台服务**保证它不被系统杀掉；应用内**两套 UI 共存**（移植版编辑器 + 夜航新界面，
设置里可切主题），聊天走 **Rust 直连 ST API**（不经 webview 网络层，
所以不碰 `SameSite` / `X-Frame-Options` 那两个坑）；ST 原生界面只留一个**逃生门**入口。

## 1. spike ① 给了哪些数（可直接用的）

| 项 | 实测值 | 对设计的影响 |
|---|---|---|
| Node 版本 | `v20.18.0`（22.23.4 编译中） | 二进制 73.7 MB |
| ST 版本 | 1.19.0 | 解包后 437 MB（`node_modules` 占大头） |
| 进程内存 | **RSS 152.4 MB**（Node 20.18）/ **186.5 MB**（Node 22.23.4，2026-10-30 实测）/ VSZ 35.0 GB | 前台服务通知要能解释这个量级；**用哪版 Node 决定写哪个数** |
| 灭屏存活 | **≥122 秒**（`setsid` 拉起，无前台服务） | 见 §3.2 |
| 监听 | 仅 `127.0.0.1:8000` | 不传 `--listen` 即默认回环（#264） |
| 启动耗时 | 未测 | 见 §6 待验清单 |

> VSZ 35 GB 是 V8 的虚拟地址预留，**不是实际占用**。设计里凡提到内存只说 RSS，
> 否则会让人以为这个 App 要 35 GB。

## 2. 应用内布局（磁盘）

```text
/data/data/<pkg>/
├── files/                      ← 可写，长期
│   ├── st/                     ← ST 1.19 解包产物（437 MB）
│   │   ├── server.js
│   │   └── node_modules/
│   └── st-data/                ← --dataRoot（用户数据：聊天/设置/角色）
└── (无 libnode.so —— 它进 APK 的 native lib 目录，只读)
```

**三条硬约束**：

1. **`--dataRoot` 必须指 `filesDir`**（上面 `files/st-data`）。
   spike 用的是 `/data/local/tmp/st-data`，那是**测试位** —— tmp 会被系统清，
   用户聊天记录放那儿等于随时可能消失。
2. **ST 首启从 APK assets 解包**，不联网下载（#262 决策：全量打包，用户对体积不敏感，
   首启二次下载才是流失点）。
3. **`libnode.so` 不打进 `files/`**，见 §4 的 W^X。

## 2.5 壳内部：两套 UI + 三个 WebView（容易混，先分清）

需求补丁 v0.1.7 §二 原文：**「TCS 客户端 UI 与「夜航」UI 共存于一个壳（编辑器页沿用移植版，
新功能页用新设计语言，设置里可切换整体主题）」**。

这一条修正了本文档第一版的一个误解 —— 我原来写"用 WebView 加载自研面板"，
听起来像"壳里只有一个页面"。实际是**同一个壳里有两套界面，且用户能切主题**。

### 2.5.1 两套 UI 的分工

| 界面 | 用哪套设计语言 | 来源 |
|---|---|---|
| 编辑器 / 审计 / 预设 / 同步（**原有功能**） | 移植版（默认沿用桌面样式，可切夜航） | T15.2 把桌面 UI 触屏化 |
| 聊天 / 卡片 / 仓库 / 我的（**四 Tab 新壳**） | 夜航 Nebula | T15.5 + T15.6 |

「设置里可切换整体主题」意味着两套**都要能在对方的语言下工作** ——
所以主题必须走 token 抽象（`design-language-nebula.md` §8 的面板主题接口），
而不是各写一套 CSS。这也是设计册 §8 存在的理由。

### 2.5.2 三个 WebView 用途（不许混）

| 用途 | 加载什么 | 走什么网络层 | 会不会踩 `SameSite` / `X-Frame-Options` |
|---|---|---|---|
| **A. 主 UI** | 我们自己的前端页面 | Tauri IPC → Rust | 不会（同源，且不是嵌 ST） |
| **B. 自研聊天面板** | **我们自己的**聊天界面 | **Rust HTTP 直连 ST API** | 不会（请求由 Rust 发出，不经浏览器） |
| **C. 逃生门** | **ST 原生 Web 界面** | webview 自己的网络栈 + v0.1.6 的 Rust 代理 | **会**，且必然踩（见 §2.5.3） |

> **最容易写错的一处**：B 和 C 都是"在应用里看聊天"，但 B 是我们的前端 + Rust 请求
> （`st-adapter` 契约那一套），C 是把 ST 的网页整个嵌进来。把 B 做成 C 就等于
> 放弃了自研面板（需求 F3 明确"不显示 ST 原生界面"）；把 C 做成 B 则逃生门失去了
> 意义（它存在的理由是 extensions / regex / 群组这些**我们没做**的功能）。

### 2.5.3 逃生门（C）

需求原文（F2）：**「ST 原生 Web 界面不做用户-facing 入口，仅保留为"高级逃生门"
（extensions/regex 等深度功能需要时使用内嵌页）」**。

| 项 | 设计 |
|---|---|
| 入口位置 | 「我的 → 高级功能（原生界面）」，**不在四 Tab 主路径上** |
| 进入前的提示 | 要说明"这是 ST 的原生界面，操作方式与 App 不同"，否则用户会以为是 bug |
| 技术前提 | **必然会重新遇到 v0.1.6 已经踩过的两个坑**（`memory.md` §19 `X-Frame-Options: SAMEORIGIN`、§20 `SameSite=Lax` 的 session cookie 在跨站 iframe 里从不发送） |
| 处置 | **v0.1.6 的 Rust 反向代理继续服役**（缩小用途）：逐条改写 `Set-Cookie` 为 `SameSite=None; Secure`、去掉/改写 `X-Frame-Options` |
| 判据 | 与 v0.1.6 同一套：面板能显示 **且** 初始化不卡在「正在初始化…」／`/api/settings/get` 不 403 |

**为什么这条不放在 T15.5 里做**：逃生门是"壳的能力"，不是"聊天面板的功能"。
它复用 v0.1.6 的代理，而那个代理的启动/端口/生命周期归壳管 —— 所以写在 T15.3。

### 2.5.4 ST 的启停与 App 生命周期

需求原文（F2）：**「随 App 生命周期启停」**。

| 事件 | ST 该怎么动 |
|---|---|
| App 首次启动 / 冷启 | 检查 → 需要则拉起（§5.2 的"先探端口"） |
| 退到后台（Home / 切走） | **不停**（这是聊天场景的核心：用户回微信再回来） |
| 用户点通知「停止」/ 应用内退出 | SIGTERM → 等 5s → SIGKILL（§5.3） |
| 系统回收进程 | 前台服务 `START_STICKY` 重建 → 走 §3.3 的端口探测分支 |
| 用户「强制停止」 | 系统杀 App；**node 可能还活着** → 下次启动靠 §5.2 的端口+身份判据复用 |

> 「随生命周期启停」不等于"退到后台就停" —— 那样聊天记录会一直断。
> 它的真实含义是「不该由用户手动去开 ST」：App 起来它就可用，用户停它就停。

## 3. 前台服务（核心）

### 3.1 为什么必须是前台服务

spike 只验了 **2 分 22 秒**灭屏存活，而且是在 `setsid` 拉起的 shell 会话里。
真实场景是「用户锁屏聊微信、半小时后回来继续」——那期间：

- **Doze** 会批量冻结后台网络与唤醒；
- 厂商 ROM（vivo 的 `i管家`、小米的「神隐模式」）会额外杀后台；
- **`exec` 出来的进程不受 Android 生命周期管理**（#276 记的官方原文），
  所以 Activity 被杀时 node 不会跟着退 —— 反过来，系统也不会替我们保它。

前台服务是目前唯一能在 Doze 下维持进程的机制（配 `START_STICKY` 与
`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 提示）。

### 3.2 通知文案（用户能看懂的版本）

```text
标题：口袋酒馆 正在运行
正文：SillyTavern 在后台待命 · 约 187 MB 内存
[停止]  [打开]
```

三条设计取舍：

- **写出「约 187 MB 内存」**：这是 Node 22.23.4 跑 ST 的实测 RSS（186.5 MB，190,988 kB）。
  若最终选 Node 20.18 则是 152.4 MB —— **这个数字跟着 Node 版本走，不要写死**。不写的话，用户在"电池用量"里
  看到一个陌生应用占 150 MB，第一反应是卸载。
- **不写端口号 / PID / 技术状态**：那是开发者关心的（与本轮 UI 文案红线同一条标准）。
- **「停止」放在通知里**：这是唯一能在应用被杀之后还能停掉 node 的入口。

### 3.3 `START_STICKY` 与重启竞态

系统杀掉前台服务后会重建它。此时**可能已经有一个 node 在跑**（如果进程没死透），
再起一个会因 `EADDRINUSE` 失败 —— 而失败信息只会出现在日志里，
用户看到的是"通知在，但页面打不开"。

处置顺序（每一步都是判据，不是"尽力而为"）：

```text
onStartCommand
  → 先探测 127.0.0.1:8000 是否已应答
      应答   → 复用，不再 exec（并记录"复用了已有实例"）
      不应答 → 起 node，等待端口就绪（超时 20s）
  → 仍不就绪 → 通知改成「启动失败，点开重试」
```

## 4. W^X 落地方案（决策 #276）

**规则**：targetSdk ≥ 29 的**应用**不能执行自己**可写目录**里的文件。

所以：

| 项 | 做法 |
|---|---|
| 可执行体 | 命名成 `libnode.so` 放进 APK 的 `jniLibs/arm64-v8a/` |
| 安装后位置 | `/data/app/.../lib/arm64/libnode.so`（**只读**） |
| manifest | `android:extractNativeLibs="true"` |
| 启动 | `ProcessBuilder` 直接执行上面那个只读路径 |
| ST 脚本 | 在 `files/st/`（可写、但**只是被 node 读，不被 exec**） |

**注意分界**：W^X 限制的是"执行可写目录里的文件"，不限制"node 去读可写目录里的
`server.js`"。所以 ST 放 `files/` 是合法的 —— 只有 `libnode.so` 本身必须只读。

> 未验：Tauri 2 的 Android 打包是否会把 `libnode.so` 正确放进 `jniLibs` 且保留可执行位。
> 这是 T15.3 第一个要打通的技术点，见 §6。

## 5. 进程与孤儿清理

### 5.1 孤儿从哪来

`exec` 出来的 node **不受 Android 生命周期管理**（#276）。三种会留下孤儿的场景：

| 场景 | 后果 |
|---|---|
| 用户「强制停止」应用 | 系统杀 App 进程，**node 可能活着**，8000 端口仍被占 |
| 应用崩溃（Java 侧） | 同上 |
| 前台服务被杀但 node 未死 | 下次启动 `EADDRINUSE` |

### 5.2 清理策略

**不做 PID 文件**。理由：应用被强制停止后再启动，PID 文件里的号可能已被系统
复用小进程 —— 拿它去 `kill` 会杀错东西，那比不清理更糟。

改为**端口 + 身份双重判据**：

```text
启动时若 8000 已有人听：
  GET /version
    → 返回 pkgVersion 且 agent 含 "SillyTavern"
        ⇒ 是我们起的那个 ST，复用（§3.3）
    → 返回别的东西 / 超时
        ⇒ 不是我们的；**不杀**，改用一个备用端口（8001、8002…）并提示用户
```

"看不懂的端口占用不杀"是刻意的：手机上 8000 被别的开发工具占了是常见情况，
而"清理不认识的进程"属于越权。

### 5.3 应用退出时

用户点通知里的「停止」或在应用内退出 → 发 SIGTERM 给 node，等 5 秒，
仍在则 SIGKILL。**只杀我们自己 spawn 的 PID**（内存里持有，不落盘）。

## 5.5 启动参数 `--browserLaunchEnabled=false` 的**原因**（2026-10-30 补）

在 vivo V2507A / Android 16 上完整跑过 ST 1.19.0，四判据全过。

⚠️ **这个参数 spike ① 当时就传了**（`spike-01-node-android.md` §7.2 的命令里有），
但文档只记了"传了什么"，**从没写过"不传会怎样"** —— 于是它看起来像个可选的开关。
本次真机复测补上了这个原因：它不是可选的。

```text
ST 在 Android 上必须传 --browserLaunchEnabled=false，不传会死
```

### A/B 对照（同设备、同 ST、同 node）

| 启动参数 | 结果 |
|---|---|
| 不带 | **进程死亡**。日志末尾 `Uncaught exception … code:'ENOENT', syscall:'spawn xdg-open'`，8000 无监听 |
| `--browserLaunchEnabled=false` | 进程存活，监听 `127.0.0.1:8000`，首页 200 |

### 机制与为什么难查

ST 监听成功后调 `open()` 打开浏览器；Android 没有 `xdg-open` ⇒ `spawn ENOENT` ⇒
**未被 catch，直接杀掉 Node 进程**。

它发生在 `listening` **之后**，所以日志会显示：

```text
SillyTavern is listening on IPv4: 127.0.0.1:8000   ← 成功
Go to: http://127.0.0.1:8000/                       ← 紧接着
Uncaught exception … spawn xdg-open ENOENT          ← 进程没了
```

**极易误判成"ST 跑不起来"或"端口被占"** —— 实际是启动成功后自杀。

⇒ T15.3 的 `ProcessBuilder` 参数列表里必须有这一项，且要有**断言**（不是注释提醒）。

> 顺带记一个打包坑：`tar --exclude='data'` 会匹配**任意层级**的 `data` 目录，
> 把 `node_modules/node-releases/data/` 一起排掉，症状是 ST 起不来且报
> `Cannot find module 'node-releases/data/processed/envs.json'`。
> 体积几乎不变（120.2 MB），所以**"包大小正常"不能证明包完整**。
> 正确写法：`--exclude='./data'`（点斜杠限定顶层）。

## 7. 环境安装（需要一次 sudo）

VM 上目前 **JDK / Android SDK / Rust 全无**（2026-10-29 实测）。

| 组件 | 版本 | 体积 | 用途 |
|---|---|---|---|
| JDK | 17（`openjdk-17-jdk-headless`） | ~300 MB | Gradle / AGP 必需 |
| cmdline-tools | latest | ~150 MB | `sdkmanager` |
| platform-34 | android-34 | ~100 MB | compileSdk |
| build-tools | 34.0.0 | ~200 MB | aapt2 / zipalign / apksigner |
| Rust | `aarch64-linux-android` target | ~50 MB | Tauri Android 编译 |

合计约 **2–3 GB**，VM 当前可用 **61 GB**，够。

### 7.1 一个可以省掉 sudo 的替代方案（供你选）

本机 Windows 上已经有 Rust 1.99.1。如果 Tauri 的 Android 构建放在**本机**：

- JDK 17 与 Android SDK 都**有免安装 zip**，解压到用户目录即可，**不需要管理员权限**；
- 好处：不用等 sudo、不影响 VM 上正在跑的 Node 编译；
- 代价：`libnode.so` 是 Linux ELF，本机只做 APK 打包没问题（它只是被打进 zip），
  但**调试时的符号/日志工具链**要在两处各备一份。

**我的倾向**：先在本机用免安装 zip 试通第 1 项（可行性验证），
通过后再决定正式构建机放哪。这样"要不要 sudo"不阻塞第一步。

## 7.5 Release 签名（T15.8 验收项，2026-10-30）

### 为什么从**第一个**测试 APK 起就必须用 release 签名

**debug 签名与 release 签名不兼容。** 用 debug 签的包装上之后，换成 release
签名的新版本**装不上去**（Android 要求更新包的签名与已装版本一致），
只能先卸载 —— 而卸载会清掉 `files/` 下的 ST 数据、角色卡与聊天记录。

所以"先用 debug 装着测试、以后再换 release"不是省事，而是
**给用户预约一次卸载重装**。测试包也必须用 release 签名。

### 密钥材料的处置

| 项 | 在哪 | 是否入库 |
|---|---|---|
| `tcs-release.jks` | `D:/tcs-release-keys/`（**仓库外**） | ✗ |
| 密码（`keystore.properties`） | 同上 | ✗ |
| SHA-256 指纹 | `vendor/android-env/RELEASE-KEY-FINGERPRINT.md` | **✓ 只留这个** |

生成：`bash vendor/android-env/gen-release-keystore.sh`
（RSA 4096 / PKCS12 / 有效期 10000 天 ≈ 27 年 / 32 字符随机密码）。

> **有效期与密钥丢失都是不可逆的。** Android 只认同一把密钥签名的新版本：
> 密钥丢了或过期了，已发布的 App **再也无法更新**，只能换包名重新上架、
> 用户数据全丢。所以必须有**两处离线备份**（脚本放一份在
> `$KEY_DIR/backup/`，第二份要人工拷到离线介质 —— 这一步脚本替不了）。

### T15.8 打包清单：必须加的签名验收项

出包时逐条核，**任何一条不成立就不发**：

- [ ] `apksigner verify --print-certs` 输出的 **SHA-256** 与
      `RELEASE-KEY-FINGERPRINT.md` 记录的**逐字相同**；
- [ ] `zipalign -c -v 4 <apk>` 通过（未对齐的包在部分机型上装不上）；
- [ ] APK 的 `signature scheme` 含 **v2 或 v3**（只有 v1 的包在 Android 11+
      上不可靠）；
- [ ] 装包后用 `adb shell dumpsys package <pkg> | grep signatures` 复核，
      与预期指纹一致；
- [ ] **同一份 keystore 连续签两个版本**，后一个能覆盖安装前一个
      （这一条才真正验证了"升级路径成立"，前四条只验证了"签名对了"）。

升级就断了 —— 而这件事**只在真正发第二个版本时才暴露**，

## ✅ 2026-10-31：APK 首次构建成功并在真机启动

上一版这份文档结尾写的是"卡在 Gradle / 无解"。**实际是有解的**，下面是最终结论。

### 唯一入口：`bash scripts/build-android.sh`

不要手工拼命令，也不要直接跑 `gradlew`。脚本里每一步都有注释说明为什么。

```bash
bash scripts/build-android.sh            # debug APK
bash scripts/build-android.sh --release  # release APK
```

产物：`client/src-tauri/gen/android/app/build/outputs/apk/arm64/debug/app-arm64-debug.apk`（约 87 MB）

### 五个此前判断错的地方

| 此前的结论 | 实际 | 为什么错 |
|---|---|---|
| 「AGP 硬拒绝非 ASCII 路径，没有配置可绕过」 | **有官方开关** `android.overridePathCheck=true` | 这个开关就写在错误消息里（`b.android.com/95744`）。我当时看到 "Please move your project to a different directory" 就认定无解，于是绕道把整个 Gradle 工程镜像到 `D:/tcs-gradle` 再手改 `rootDirRel`。**那套做法白费了** —— `tauri android build` 坚持在自己的 `gen/android` 里跑 |
| 「不能直接 `gradlew`，要先有 `cli-options-server.json`，那个文件手工造不出来」 | 对，但**只对 `android-studio-script` 成立**。外层 `tauri android build` 会自己起这个服务 | 我只试了内层命令，没试外层入口 |
| 「`compileSdk` 必须降到 36 是因为本机只装了 34」 | 依赖下限**真的就是 36**（Tauri 插件 AAR 写 `36 or later`）；37 是 init 写的默认值，本机没有，会触发 20 分钟以上的 SDK 下载（实测 ~120 KB/s） | 结论对、理由错。这种"结论对但归因错"最危险：下次遇到"依赖要求更低版本"时会照着错理由降过头 |
| 「中文路径问题只能靠 `CARGO_TARGET_DIR` 绕」 | 对，但**只针对链接器**。AGP 的路径检查是另一件事，用 overridePathCheck | 之前把两个不同层的问题当成一个 |
| 「`BuildTask.kt` 里 `node tauri ...` 是这台机器的特例」 | 是特例，但**每次 `tauri android init` 都会重现**（`gen/` 在 gitignore 里） | 所以修法必须是可重跑脚本，不能手改 |

### 四个只有真跑才会暴露的新问题

1. **rustc ICE**：多次中断的构建把 `incremental/` 写坏（伴随 `error copying object file ... 拒绝访问 (os error 5)`），之后报
   `thread 'rustc' panicked at rmeta/encoder.rs:2486: no entry found for key`。
   → `CARGO_INCREMENTAL=0` 绕过整条复用路径。

2. **缺 `mobile_entry_point`**：Tauri CLI 打包前会校验 `.so` 里的 JNI 符号，报
   `does not include required runtime symbols`。
   → `lib.rs` 的 `run()` 加 `#[cfg_attr(mobile, tauri::mobile_entry_point)]`。
   这个错此前一直没露出来，因为内层 `android-studio-script` 先被 BuildTask 的
   `Cannot find module '...\tauri'` 挡住了，根本没跑到校验这一步。

3. **★ jniLibs 里的 `.so` 是 0 字节**：CLI 打印 `Info symlinking lib ...` 看着成功，
   落地文件却是 0 字节，而 gradle 照样打包成功、CLI 不报错。
   → `UnsatisfiedLinkError: dlopen failed: ... is empty` 的 APK，**构建日志全绿**。
   脚本里用真实字节覆盖后跳过 `rustBuild*` 重新打包。

4. **`.so` 里内嵌的前端会过期**：Tauri 2 在 Android 上把前端资源嵌进 `.so`（不是放 `assets/`）。
   用了 `-x rustBuild*` 就跳过了嵌入步骤 —— dist 已经是 `rules-DI7_8aP1.css`，
   `.so` 里还是 `rules-CvhQVdo9.css`，**改了半天界面一点变化都没有**。
   脚本按 dist 里的真实文件名去 `.so` 里找，缺一个就重跑一次嵌入。

**这四条的共同点：判据只能落在解包后的字节上。** 日志全绿、APK 存在、体积看着正常（46 MB，
被 `libnode.so` 的 99 MB 撑着），全都不能说明产物可用。

### 真机验证到哪一步

设备：Redmi Note 8 Pro / Android 11 / arm64-v8a（与 Spike ① 同一台）。

| 项 | 结果 |
|---|---|
| `adb install` | ✔ Success |
| 启动后进程存活 | ✔ `com.taverncardstudio.client` 常驻，RSS 287 MB |
| 前端加载 | ✔ `http://tauri.localhost/` 已渲染（`assets/rules-*.js` 有执行日志） |

| **竖屏布局** | ❌ **旧的桌面布局被塞进竖屏，顶栏右侧按钮被屏幕边缘切掉** |

最后一条是这轮发现的真问题：编辑器是桌面优先做的，`@media` 只有 1080 断点
（另两处是 `prefers-reduced-motion`），从没打算放进 392dp 的竖屏。

已在 `client/src/styles.css` 加 `@media (max-width: 640px)`：顶栏按钮区改为占满整行并
折行、正文强制上下堆叠、审计面板分隔线从竖改横、弹窗放宽。

**但这一改还没在真机上验证到** —— 打包过程中 adb 掉成 `offline`（USB 侧问题，

所以「窄屏断点生效」目前**只有代码和 dist 里的证据，没有真机截图**。

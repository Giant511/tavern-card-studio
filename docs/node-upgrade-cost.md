# 「升 Node 要重趟构建」的成本实测

> 决策 #261 写着「代价是每次升 Node 要重新趟一遍 `android-configure` + `make`」。
> 这条一直是**定性**的判断，没有数字。2026-10-29 做了第二次（20.18.0 → 22.23.4），
> 这是要填进决策表的实测成本。
>
> 状态：**22.23.4 编译进行中**，本文随进度回填。

## 2. 20.18.0：5 小时以上，但里面大半不是编译

| 阶段 | 耗时 | 其中有多少是"编译" |
|---|---|---|
| `-j2` 跑到 2983 个 `.o`（含 VM 失联期） | 1h52m | 2 vCPU，慢一倍是环境所致 |
| `-j4` 续跑（host V8 + v8_initializers + target 收尾） | 3h20m+ | **这一段才是 4 核的真实速度** |
| 合计 | **5h+** | 原估 1.5–2.5h，**错了两倍多** |

**估错的根因**（值得单独记）：漏算了 **V8 要编两遍**。
交叉编译时 V8 生成两套目标文件 —— `obj.host/`（跑 mksnapshot）与
`obj.target/`（最终产物），而最大的 `v8_initializers` 是 torque 生成的
**455 个 `.cc`，host 与 target 各编一遍**。合计约 **4700+ 个目标文件**，
不是按源码文件数估的 2000 多个。

原估算方法是「71 KB 文件编译 4.29 秒 → 外推」，而那个基准是**单个小文件**；
V8 的目标文件里大量是模板密集的巨文件（`builtins-*-tq-csa.cc`），
单文件最慢能到几分钟。

**这一轮还含这些非编译开销**：四个功能缺陷的定位与修复、
`-j2` 白跑一半后 `SIGTERM` + 删 21 个可能截断的 `.o`、VM 整机失联后恢复。

### 3.1 这一轮踩到的坑（不属于"编译"，属于"换版本"）

**坑① gyp 换了 `config.gypi` 的输出风格 —— 这是换大版本的必然代价**

```text
20.18.0:   'target_arch': 'arm64',        ← Python repr，单引号
22.23.4:   "target_arch": "arm64",        ← JSON，双引号
```

而且 20.18 还把两个键挤在一行：`  'variables': { 'OS': 'android',`

脚本里三行单引号模式的 `grep` 在 22 上**取到空值**，
而 `set -euo pipefail` 让 `VAR=$(grep … | head | sed)` 这种赋值
**静默失败并退出整个脚本**：日志只停在 `== 配置自检 ==`，
**一个错误字都不打**，进程消失，`pgrep` 什么都查不到。

修：`gyp_var()` 同时吃单双引号，且**不锚定行首**
（`^[^:]*` 会被 20.18 那种一行两个键的写法卡住）。

**坑② 引号内的路径不展开（连踩两次）**

| 写法 | 结果 |
|---|---|
| `WORKDIR='~/tcs-build/work-22.23.4'` | 引号内 `~` 不展开 ⇒ 建出字面 `~` 目录 |
| `WORKDIR='$HOME/tcs-build/work-22.23.4'` | **单引号**内 `$HOME` 也不展开 ⇒ 建出字面 `$HOME` 目录 |

两次都表现为「RESUME 检查报没有可续跑状态」——**而这个结论本身是错的**。
修：启动前 `echo $HOME` 拿真实值，拼绝对路径。

> 这是 `~` 不展开这条根因的**第三次**发作（前两次：SFTP、scp）。

### 3.2 这一轮的第二个代价：**ICU data 那个单文件把 clang 搞崩了**

编译在 84 分钟时**失败退出**（不是卡住）：

```text
clang-17: error: clang frontend command failed with exit code 135
make: *** [tools/icu/icudata.target.mk:159: .../icudt78_dat.o] Error 1
```

`exit 135` = 128 + 7 = **SIGBUS**。崩溃点在 `clang::ParseAST`（解析阶段），
并留下复现脚本 `/tmp/icudt78_dat-aff915.sh`。

#### 事实

| 项 | Node 20.18.0 | Node 22.23.4 |
|---|---|---|
| ICU 版本 | 75.1 | **78.3** |
| `icudt*_dat.c` 源文件 | 92,078,781 B（87.8 MB） | **98,692,328 B（94.1 MB）** |

**只大了 7%，20.18 编过了，22 崩了。** 所以真因不是"文件变大"，而是：

> `-O3` 编译这个 94 MB 的单文件峰值很高，**与 `-j4` 的其他 3 个 job 叠加**后
> 超过 5.9 GB 内存 + 12 GB swap ⇒ mmap 失败 ⇒ SIGBUS。

#### 结论一：这是**概率性**失败，而概率性更危险

同一台机器、同样的 `-j4`，20.18 那轮编过了（因为它是在 `-j2` 阶段编的）。
所以这个错误的表现是：

```text
崩了 → 你重跑一次 → 这次恰好没撞上 → 以为解决了 → 下次换版本又崩
```

**它不会稳定复现**，所以"重跑就好了"是最坏的结论。必须当成结构性限制处理。

#### 结论二：修法与实测数据

单文件降优化级别（`-O3` → `-O1`）。它只是 **ICU 的数据数组**，
`-O3` 对一个纯数据段几乎不产生收益，但内存差一倍以上。

| 项 | `-O1` 实测 |
|---|---|
| 峰值内存（Maximum resident set size） | **2,469,328 KB ≈ 2.35 GB** |
| 耗时 | **4 分 24 秒** |
| 产物 | 33,108,880 字节 |

**一个容易误判的细节**：崩溃时 `icudt78_dat.o` **已经存在且大小正确**（33,108,880 B）——
它是"边写边崩"的完整产物。所以：

> ⚠️ **看到 `.o` 存在，不能认为这个 TU 成功了。** 必须看 make 的退出码。
> 更糟的是，如果 make 因为 `.o` 时间戳比源新而跳过它，那份**没验过的** .o 会直接进链接。

处置：
1. 删掉崩溃留下的 `.o` 与依赖文件；
2. 用 `-O1` 重编该文件（带 `-MMD -MF` 生成依赖，否则 make 会因缺 .d 重编）；
3. **并行度降到 `-j2`** 续跑剩余部分（避免再次峰值叠加）。

#### 结论三：这条要进构建脚本

现在这套处置是**手工**做的（本次），下次换 Node 版本还得重来一遍。应该固化：

- 脚本里对 `obj/gen/icudt*_dat.c` 这一个 TU 单独特判，用独立（低）优化级别编；
- 或者全局把 `-j` 上限按"最大单文件内存 × 并行数 ≤ 可用内存"再卡一道
  —— 现有公式只按 CPU 与总内存估，**不知道有 94 MB 的单文件**。

> **已编码（2026-10-30）**。三条处置都写进脚本并在真构建树上验证过，
> 不再是技术债。落地方式与"为什么不能那样写"见下一节。

### 3.2.1 三条处置的落地形态（2026-10-30，含两个被推翻的做法）

| # | 处置 | 落在哪 |
|---|---|---|
| ① | 该 TU 单独 `-O1` | **源码** `tools/icu/icu-generic.gyp` 的 `icudata` 目标（补丁 4） |
| ② | 并行度按"单文件峰值"再卡一道 | `build-node-android.sh`：超大 TU 在场时压到 `-j2` |
| ③ | 续跑前无条件重编该 `.o` | `build-node-android.sh`：`find out -name 'icudt*_dat.o*'` 全删 |

#### 被推翻的做法 A：改生成的 makefile

第一版在 configure 之后给 `out/tools/icu/icudata.target.mk` 追加：

```make
$(OBJS): GYP_CFLAGS += -O1
```

grep 得到、看着对。但**它是生成物**：一次 `make -B`（甚至 `make -B -n` dry run）
就会让 make 重新生成 `out/` 下的 `*.mk`，补丁**静默消失**。
实测：`grep -c O1` 从 1 变 0，文件 mtime 变成那次 dry run 的时刻。

后果特别坏：构建跑到 84 分钟又崩一次，而"我明明打过补丁"会让人往别处找原因。

#### 被推翻的做法 B：只在 gyp 里写 `'cflags': ['-O1']`

gyp 把**目标自己的** `cflags` 放在继承来的全局 cflags **之前**。实测生成的
`CFLAGS_Release` 里 `-O1` 在第 175 行、`-O3` 在第 184~189 行 ——
clang 以**最后一个** `-O` 为准，所以 `-O3` 胜出，补丁等于没打。

正确写法要两条一起：

```python
'cflags!': [ '-O3' ],   # gyp 的"从继承列表里删掉这个标志"
'cflags':   [ '-O1' ],
```

改完实测：`CFLAGS_Release` 里只剩 `-O1`（第 188 行），`-O3` 计数 **0**。

#### 断言本身也修过两次（都属"绿而无用"）

脚本在 make 之前会断言"这个 TU 确实是 -O1"，失败就当场退出 —— 不要烧 17 小时再崩。
这条断言的第一版**恒为真**，两次才修对：

1. 写的是 bash 双引号里的 `"^\s*-O3 \\*$"`。bash 会把 `\\` 折成 `\\`→`\`，
   正则变成"字面星号"，**永远匹配不上**。改成单引号 + POSIX 字符类。
2. 改成单引号后仍全文件 `grep`，而 Debug 块里也有 `-O1` —— 把 Release 块里的
   `-O1` 删掉照样通过。改成先用 `awk` 只抽 `CFLAGS_Release` 那一块再匹配。

最终用变异测试验过：Release 块内把 `-O1` 改 `-O3` → ✘；删掉 `-O1` → ✘；正常 → ✓。

#### ③ 的路径也不能写死

第一版写 `out/Release/obj/gen/icudt*_dat.o` —— 那是**生成的 .c/.S 所在目录**。
真正的目标文件在 `out/Release/obj.target/icudata/gen/icudt78_dat.o`
（gyp 的 `$(obj).$(TOOLSET)/$(TARGET)` 布局）。

那次"已清 1 个残留"其实是把我为测试造的假文件删了 —— **假阳性**：
真崩溃产物没删，make 会因时间戳跳过它，坏 `.o` 直接进链接。
现在用 `find out -name 'icudt*_dat.o*'`，实测能清掉 3 个真实残留（`.o` / `.d` / `.d.raw`）。

#### 顺带修掉的一个隐患：补丁顺序

补丁 1、4 改**源码**，补丁 2、3 改**生成物**。一次全跑会得到
"4 还没生效、2/3 已被重新生成覆盖"。现在补丁脚本有 `PATCH_PHASE`：

| 阶段 | 补丁 | 时机 |
|---|---|---|
| `source` | 1、4 | configure **之前**（gyp 生成时才把它变成 `-O1`） |
| `generated` | 2、3 | configure **之后** |

`build-node-android.sh` 已按阶段调用（此前它**根本没调用过补丁脚本**，
等于从零跑一次构建必挂）。

## 3.3 第三个坎：gyp 条件回归（本节是「升 Node」最贵的一项）

Node 22.23.4 把 20.18 里一批**平台相关源文件**的收录条件从 `host_os` / `target_os`
改成了 `OS`。交叉编译到 Android 时 `OS == "android"`，于是这些文件**被静默丢弃**。

### 表现：编译全过，只在链接期炸

```
undefined reference to `v8::internal::trap_handler::TryHandleSignal(...)`
undefined reference to `v8::internal::trap_handler::RegisterDefaultTrapHandler()`
undefined reference to `v8_internal_simulator_ProbeMemory`
ld.lld: error: undefined symbol: android_getCpuFeatures
```

5708 个 TU **全部编译成功**，`mksnapshot` 和 `node` 的链接各失败一次。

### 两处具体差异

| | Node 20.18（能过） | Node 22.23.4（失败） |
|---|---|---|
| `handler-outside-simulator.cc` 条件 | `_toolset=="host" and host_arch=="x64" and (host_os=="linux" or ...)` | `(_toolset=="host" and host_arch=="x64" or _toolset=="target" and target_arch=="x64") and (OS in "...")` |
| host mk 里收录数 | 3 个 trap-handler 文件全在 | **0 个**（连 `handler-inside-posix` 也缺）|
| `cpu_features_ndk.o` | 在 `node.target.mk` 的 LIBS 里 | **完全没有** |

### 为什么容易漏诊

- 报错只提"符号未定义"，**不提是哪个文件没编**；
- 报错列出的符号 ≠ 缺失文件的清单（我第一版只补了 2 个文件，漏了 `handler-inside-posix.cc`，
  因为 `TryHandleSignal` 只在那个文件里定义，而报错里它和另外两个符号混在一起）；
- 干跑 `make -n` **不能**用来判断"还差什么"，增量场景下它不生成 `.d`，会虚报几千个待编对象。

### 修法（已固化为脚本）

`vendor/node-android/apply-node22-android-patches.sh`，三个补丁，幂等：

1. `handles.h` —— clang 17.0.2 的 CWG2518 缺陷（V8 12 的"友好诊断"）；
2. `v8_base_without_compiler.host.mk` 补 3 个 trap-handler 对象；
3. 手工编 NDK 的 `cpu-features.c` → `cpu_features_ndk.o`，并补进 `node.target.mk` 的 LIBS。

> ⚠️ 第 2、3 项改的是**生成物**（`out/*.mk`）。重跑 `android-configure` 会全部覆盖，
> 所以脚本必须在 **configure 之后、make 之前**跑。
> 根治要改 `v8.gyp` / `node.gyp` 里那些 `OS` 判断，属更大的改动，本轮未做。

> ⚠️ 补 `LIBS` 段时**必须自己补续行反斜杠**：`-landroid` 原本不带 `\`，
> 直接追加新行会让 make 报 `recipe commences before first target`。这个错我犯过一次。

## 4. 结论

### 4.1 实测总账

| 项 | 值 |
|---|---|
| **产物** | `.verify/node-arm64-22.23.4`，**99,498,384 字节（99.5 MB）**，strip 后 |
| 对照 20.18 | 77,238,720 字节（73.7 MB）⇒ **+25.8 MB**（V8 12 + ICU 78） |
| 三条判据 | `e_machine=0x00b7`(AArch64) / `/system/bin/linker64` / `liblog.so` —— **本机独立复核** |
| **总耗时** | **约 17.6 小时**（首轮 8.3h + 补丁后重编 8.7h + gyp 修复 0.6h） |
| 首跑 20.18 对照 | 约 5 小时（含 4 个缺陷排查） |

### 4.2 「升 Node」的真实成本结构

**纯编译时间不是主要成本。** 17.6 小时里：

| 类别 | 时长 | 占比 |
|---|---|---|
| 必要编译（-j2，2782+ TU） | ~13 小时 | 74% |
| ICU 单文件降级重编 | 0.1 小时 | <1% |
| **改 `handles.h` 触发的 near-full rebuild** | 8.7 小时 | 49%（与上重叠） |

> 关键教训：**改一个被普遍 include 的头文件，等价于重编一遍。**
> 如果早点把 `handles.h` 的补丁和 gyp 修复**一起**做完再重新 make，
> 总时长能压到 ~13 小时。分批修 = 分批全量重编。

### 4.3 下一次升 Node 应该怎么做（按顺序，别跳）

1. `android-configure` 之后**立刻**跑 `apply-node22-android-patches.sh`（三个补丁一次打完）；
2. `make -j2`（`-j4` 会在 ICU 那个 94 MB 单文件上 SIGBUS）；
3. 若 ICU 报 `exit 135`：删 `.o` + `.d.raw`，`-O1` 单编该文件；
4. **不要**用 `make -n` 估剩余量，看 target 侧的最后几个大组有没有开始；
5. 判断"完成"必须三条同时成立：`make` 退出 + 产物存在 + 新增 error 为 0。

### 4.4 一句话

**升 Node 的代价不在"编得久"，在"上游 gyp 在 Android 交叉编译下是坏的，
而它只在链接期暴露"。** 三个补丁必须一次性打全 —— 分批打的代价是反复全量重编。
